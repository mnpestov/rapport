# Процесс: парсинг цены/скидки/подробностей по авторам

Этот файл описывает текущий итеративный процесс добавления полей
`Pattern.details` (raw: "Подробности"), `Pattern.price` и `Pattern.oldPrice`
для уже подключённых авторов каталога. Ориентирован на то, чтобы **любая
модель**, не видевшая предыдущих сессий, могла подключиться к работе и
продолжить её без потери контекста.

Смежные файлы:
- [author_parsing_checklist.md](author_parsing_checklist.md) — статус по
  каждому автору (галочка + короткая заметка), обновляется после каждой
  итерации.
- [author_parsing_notes.md](author_parsing_notes.md) — технические детали
  парсинга по каждому автору (селекторы, разметка, edge-cases), дополняется
  после каждой итерации.
- [author_sync_lib/confirmed_authors.py](author_sync_lib/confirmed_authors.py) —
  **единый источник правды**: список авторов с подтверждённой ценой+скидкой+
  подробностями (`CONFIRMED_AUTHORS`). Используется и SQL-генератором, и
  ежедневным проверщиком цен — правится только этот файл, не копии списка.
- [generate_prod_backfill_sql.py](generate_prod_backfill_sql.py) →
  [prod_details_price_backfill.sql](prod_details_price_backfill.sql) —
  генератор и результирующий SQL-патч для прода.
- [check_price_updates.py](check_price_updates.py) — отдельный от
  `author_sync.py` скрипт, предназначен для ежедневного автозапуска (cron
  на проде): перечитывает `Pattern.price`/`oldPrice` у уже опубликованных
  паттернов авторов из `CONFIRMED_AUTHORS` и обновляет при расхождении.
  Ничего не знает про конкретных авторов — целиком опирается на
  `extract_price_any_known_platform` (`author_sync_lib/hooks.py`), общую
  цепочку всех уже реализованных механизмов цены. См. раздел ниже.
- `author_sync_lib/` — сам скрапер (модульный пакет, `author_sync.py` в
  корне `scripts/` — тонкая обёртка с CLI).

## Зачем это нужно

`Pattern.details` — длинный текст "Подробности", который раньше вообще не
собирался. `Pattern.price`/`Pattern.oldPrice` — абсолютные значения в
рублях (не флаг скидки — активная скидка вычисляется на фронте как
`oldPrice > price`). Для новых карточек (новинок) это должен заполнять сам
скрапер при обнаружении; для уже опубликованных паттернов — заполняется
бэкфиллом отдельно.

**Цена = 0 значит "бесплатно"** — не отображается на фронте как цена, а
превращается в бейдж "Бесплатно" (`Pattern.isFree`). Обрабатывается ОДНОЙ
общей функцией `normalize_free_price(price, old_price)`
(`author_sync_lib/utils.py`) — используется во всех трёх местах, где цена
попадает в БД (обогащение новинок в `main()`, `backfill_details()`,
`check_price_updates.py`), так что при добавлении цены под нового автора
отдельно про это думать не нужно, если писать цену через один из этих трёх
путей. Правило одностороннее: `price == 0` → `isFree = True`, но
`isFree`, уже стоящий `True` в БД (например, вручную поставленный админом
по причине, не связанной с ценой), НИКОГДА не откатывается обратно в
`False`, даже если извлечённая цена теперь ненулевая — см.
`is_free or db_is_free` в обоих местах записи. На фронте (`PatternCard.tsx`,
`PatternDetails.tsx`) цена дополнительно скрывается, если `isFree === true`,
независимо от значения `price` — не показывать одновременно бейдж и цену.

## Общая схема итерации по одному автору

Работа идёт **по одному автору за раз**, не пачками — так проще держать в
голове специфику конкретной вёрстки и живьём всё проверять.

1. **Пользователь присылает разметку.** Заходит на сайт автора в DevTools,
   копирует HTML для (а) цены — обычно два варианта: без скидки и со
   скидкой, если скидка вообще встречается у этого автора; (б) блока
   "Подробности". Если что-то в тексте должно быть исключено (доставка,
   копирайт, реквизиты и т.п. — повторяющийся по всем товарам boilerplate),
   тоже указывается явно.

2. **Модель пишет обработчик** в `author_sync_lib/`:
   - Если разметка — это **известная общая платформа** (WooCommerce,
     "js-description"-конструктор — см. `author_parsing_notes.md`), **не
     плодить дублирующий код под одного автора** — расширять существующую
     общую функцию (`_extract_woocommerce_price`,
     `_extract_js_description_platform_price` и т.п. в `hooks.py`). Это уже
     дважды окупилось: WooCommerce-механизм и js-description-механизм
     сразу заработали на ~10 других авторов без доп. работы.
   - Если разметка **специфична для одного сайта** — новая функция вида
     `_extract_<author>_price(soup)` / `_<author>_exclude_details_paragraph(text)`
     в `hooks.py`, подключается через `DOMAIN_CRAWL_HOOKS['<домен>']`.
   - Цена подключается в `crawlers.py` → `fetch_and_parse_detail` цепочкой
     `if p['price'] is None: p['price'], p['oldPrice'] = _extract_XXX_price(...)`
     — так несколько механизмов мирно сосуществуют, не мешая друг другу
     (на не-своей платформе просто не находят нужных селекторов и
     возвращают `None, None`).
   - Исключение boilerplate-параграфов — через хук
     `exclude_details_paragraph(text) -> bool`, вызывается для каждого
     `<p>`/`<li>`/`<tr>`-блока в `_extract_details_text`.

3. **Живая проверка — ОБЯЗАТЕЛЬНА, не полагаться на логику "на бумаге".**
   На этот процесс уже несколько раз попадались реальные баги, которые
   проверка "по коду" не поймала бы:
   - разница между текстом, который прислал пользователь, и тем, что
     реально отдаёт сайт (падежи, "электронную почту" vs "почту" и т.п.);
   - скрытые/задвоенные элементы (`hidden`-атрибут у "старой цены", которая
     физически всегда присутствует в DOM независимо от того, активна ли
     скидка);
   - общий контейнер, где помимо нужного текста лежит виджет "похожие
     товары" с чужими ценами.

   Практика: написать маленький Python-скрипт, дергающий
   `fetch_and_parse_detail(...)` (или конкретную extract-функцию) напрямую
   против реального URL — без БД, без полного `main()`. Быстро, дёшево,
   ловит реальные расхождения.

4. **Прогнать полную регрессию** `--sample-details` (см. ниже) — особенно
   важно, если менялась ОБЩАЯ функция (например `_extract_details_text`),
   а не только новый домен-специфичный хук. Сравнить `sample_details.md` до
   и после правки. Разница должна объясняться: (а) ожидаемым улучшением
   для текущего автора, (б) дрейфом контента живого сайта между двумя
   прогонами (нормально — сайты меняются), либо быть явно расследована как
   баг.

   Забавный урок этой сессии: расширение `_extract_details_text` под
   Hollywool (добавили сбор `<li>`/`<tr>`, не только `<p>`) сначала было
   заведено на условии "если нашли хоть один p/li/tr — не откатываться к
   fallback на весь контейнер" — и это тихо съело контент у авторов, чей
   единственный совпавший контейнер не содержит `<p>` вовсе, а содержит
   ОДИН случайный `<tr>` из внутренней Tilda-вёрстки (например, обёртку
   кнопки "В корзину"). Починили, завязав ветку "расширенного" извлечения
   строго на наличие `<p>` — как было раньше — и лишь ВНУТРИ неё
   дополнительно собирая `<li>`/`<tr>`.

5. **Бэкфилл в ЛОКАЛЬНУЮ dev БД** — сразу после того, как обработчик
   проверен вживую:
   ```bash
   cd apps/backend/src/scripts
   DATABASE_URL="postgresql://postgres:postgres@localhost:5434/knitting_catalog" \
     python3 author_sync.py --backfill-details "<Имя автора>"
   ```
   Заполняет `details`/`price`/`oldPrice` для уже опубликованных паттернов
   этого автора. Идемпотентно (`WHERE details IS NULL OR price IS NULL`) —
   безопасно перезапускать.

6. **Добавить автора в `author_sync_lib/confirmed_authors.py`**
   (`CONFIRMED_AUTHORS`) и перегенерировать SQL-файл для прода:
   ```bash
   DATABASE_URL="postgresql://postgres:postgres@localhost:5434/knitting_catalog" \
     python3 generate_prod_backfill_sql.py
   ```
   Файл `prod_details_price_backfill.sql` перегенерируется **целиком** из
   `CONFIRMED_AUTHORS` — не редактируется руками, не дописывается вручную.
   Выполняется на проде **вручную, самим пользователем**, уже ПОСЛЕ деплоя
   миграции схемы (колонки `details`/`price`/`oldPrice`) и кода скрапера.

   Тот же `CONFIRMED_AUTHORS` автоматически расширяет область действия
   `check_price_updates.py` (ежедневный проверщик цен, см. ниже) — отдельно
   его никуда добавлять не нужно.

7. **Обновить документацию**: галочку и заметку в
   `author_parsing_checklist.md`, технический разбор в
   `author_parsing_notes.md`.

8. **Следующий автор** — пользователь присылает новую разметку, цикл
   повторяется.

## Ежедневный проверщик актуальности цены (`check_price_updates.py`)

Отдельный от `author_sync.py` скрипт — не часть общего процесса добавления
новых авторов, а фоновый job для уже добавленных. `author_sync.py`
занимается только НОВИНКАМИ (обнаружение + очередь модерации); цена на уже
опубликованных паттернах могла с тех пор измениться на сайте автора
(появилась/закончилась скидка, изменилась цена) — этот скрипт закрывает
именно этот разрыв.

**Как устроен:**
- Берёт список авторов из `CONFIRMED_AUTHORS`
  (`author_sync_lib/confirmed_authors.py`) — того же, что использует
  SQL-генератор.
- Для каждого автора — только **видимые** (`isVisible = true`) паттерны с
  `url`. Черновики и очередь модерации не трогает вообще.
- Цену извлекает через `extract_price_any_known_platform(soup)`
  (`author_sync_lib/hooks.py`) — общую цепочку всех уже реализованных
  механизмов (сейчас: WooCommerce → js-description-платформа →
  hollywool.ru). **Этот скрипт ничего не знает про конкретных авторов** —
  когда для нового автора появляется свой хук цены, единственное, что
  нужно сделать, — вписать его в цепочку внутри
  `extract_price_any_known_platform`; `check_price_updates.py` подхватит
  его автоматически, без единой правки в самом файле скрипта.
- При расхождении с БД — `UPDATE` только `price`/`oldPrice`, `details` не
  трогает.
- Пишет отчёт `price_check_report.md` (что изменилось, какие ошибки) —
  тот же стиль, что `sample_details.md`/`sync_stats.md`.

**CLI:**
```bash
# все CONFIRMED_AUTHORS:
DATABASE_URL="..." python3 check_price_updates.py
# только один автор (ручная проверка):
DATABASE_URL="..." python3 check_price_updates.py "Имя автора"
```

**Cron на проде** — рекомендация в шапке самого файла (не настраивается
автоматически, устанавливается пользователем при деплое):
```
0 4 * * * cd /var/www/rapport/apps/backend/src/scripts && python3 check_price_updates.py >> /var/log/rapport/price_check.log 2>&1
```

**Проверено вживую** (на локальной БД): прогон по реальному автору (0
изменений — цена не менялась), затем принудительно испорчена цена одного
паттерна в БД напрямую и перезапущено — скрипт корректно обнаружил
расхождение, восстановил правильное значение с сайта и записал изменение
в отчёт.

## Границы ответственности (важно!)

- **Прод-БД — только чтение** напрямую (через SSH + `psql`, read-only
  SELECT). Никаких write-операций на проде через код в рамках этого
  процесса — только через заранее подготовленный и вручную запущенный SQL
  файл, и только когда пользователь явно это делает сам.
- **Локальная dev БД** (Docker, `miniapp_uu-db-1`, порт 5434) — можно
  писать свободно, это песочница.
- Деплой (`git add`/commit/push/`deploy.sh` на сервере) всегда делает сам
  пользователь. Модель может подготовить точный список файлов и текст
  коммита, но не выполняет `git push`/деплой самостоятельно.
- Прод ещё не деплоился с изменениями по `details`/`price`/`oldPrice` (по
  состоянию на момент написания) — соответственно прод-SQL файл пока
  нигде не запускался.

## Быстрые команды

```bash
cd apps/backend/src/scripts

# Полный live-прогон превью "Подробности" + цена по 1-2 товарам на автора,
# ничего не пишет в БД, сохраняет sample_details.md:
DATABASE_URL="postgresql://postgres:postgres@localhost:5434/knitting_catalog" \
  python3 author_sync.py --sample-details

# Бэкфилл уже опубликованных паттернов конкретного автора (локальная БД):
DATABASE_URL="postgresql://postgres:postgres@localhost:5434/knitting_catalog" \
  python3 author_sync.py --backfill-details "Имя Автора"

# Перегенерировать SQL-патч для прода (после добавления автора в
# CONFIRMED_AUTHORS внутри author_sync_lib/confirmed_authors.py):
DATABASE_URL="postgresql://postgres:postgres@localhost:5434/knitting_catalog" \
  python3 generate_prod_backfill_sql.py

# Ежедневный проверщик цены/скидки — ручной прогон (все CONFIRMED_AUTHORS
# либо один автор вторым аргументом):
DATABASE_URL="postgresql://postgres:postgres@localhost:5434/knitting_catalog" \
  python3 check_price_updates.py ["Имя Автора"]

# Проверка синтаксиса пакета после правок:
python3 -m py_compile author_sync_lib/*.py author_sync.py
```
