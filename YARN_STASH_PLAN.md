# Хранилище пряжи пользователя — план (v1, черновик)

Документ только для планирования. Кода не меняет. Задача: спроектировать
платную страницу «Хранилище пряжи» (по аналогии с приложением Хомяк) —
личный инвентарь артикулов пряжи пользователя со свотчами (образцами) и
подбором подходящих описаний из каталога Раппорта.

Собрано на основе изучения текущего кода: `apps/backend/prisma/schema.prisma`
(модели `Yarn`, `Permission`, `UserPermission`, `PatternYarn`, `Draft`/
`DraftYarn`), `yarnsController.ts` (`createAuthorYarn`, `suggestYarns`),
`requirePermission.ts` (`requirePermissionOrAdmin`), пайплайна изображений
(`imagePipeline.ts`, `patternImages.ts`, `admin.ts` `/admin/upload`) и фронтового
`ImageGalleryManager`/`ImageCropper`.

> **Не путать с `Permission.PREMIUM_YARNS`** — уже реализованным флагом
> (коммит `c9b280d`), который гейтит показ списка артикулов пряжи *из
> справочника* внутри карточки описания паттерна. Это другая фича, никак не
> связанная с личным хранилищем пользователя. Новый флаг из этого плана
> назван `PREMIUM_YARN_STASH`, чтобы не путаться при чтении enum.

## 1. Решения, зафиксированные с пользователем

1. **Доступ** — все роли (`USER`/`AUTHOR`/`ADMIN`), не завязано на роль.
2. **Разрешение** — новый отдельный флаг `Permission.PREMIUM_YARN_STASH` (по образцу
   `PRICE_ALERT`), выдаётся/снимается вручную через существующие бэкенд-ручки
   `GET/POST/DELETE /admin/permissions` — новых бэкенд-ручек для выдачи не
   требуется, только новое значение enum. **Уточнено внешней проверкой плана
   против кода: это верно только для бэкенда.** UI админки
   (`apps/admin/src/pages/Users/Users.tsx:65-140`, `PermissionsSection`)
   хардкодит отдельный `useState` + чекбокс + вызов `syncPermission` на
   каждое разрешение (`PREMIUM_CORE`, `PREMIUM_DETAILS`, `PREMIUM_YARNS`,
   `PREMIUM_EXTRA`, `WEB_ACCESS`, `PRICE_ALERT`) — новое значение enum само
   по себе не появится в UI. Нужен новый `useState` + чекбокс +
   `syncPermission(user.id, "PREMIUM_YARN_STASH", ...)` по образцу
   существующих (см. T16 в Implementation Tasks) — без этого фичу физически
   некому включить даже в закрытом ADMIN-only тестировании (§5.2).
3. **Пользовательские артикулы, которых нет в справочнике** — пишутся в общий
   `Yarn` со `status: PENDING`, тем же путём, что уже есть у авторов
   (`createAuthorYarn`, `POST /author/yarns`). Модерация — тем же интерфейсом
   очереди, что и сейчас (`GET /admin/yarns?pending=1`, `approveYarn`,
   `rejectPendingYarn`/`mergeYarn`).
4. **Модель партии/цвета** — один артикул пряжи может встречаться в хранилище
   пользователя несколько раз (разный цвет, разная партия одного и того же
   `Yarn`) — отдельные записи `StashSkein`, сгруппированные по `yarnId`.
5. **Запас** — храним остаток и ведём лог расхода (списание по граммам/моткам),
   как в Хомяке. Расход опционально ссылается на `Pattern` («связала свитер —
   ушло 350 г»).
6. **Свотч (образец)** — вложенная сущность на артикул (может быть несколько
   на один `StashSkein`): фото, спицы, плотность **отдельно до и после ВТО**
   (петли/ряды на 10×10, тот же формат чисел, что у `Pattern.densityStitches`/
   `densityRows`).
7. **Подбор описаний под пряжу** (v1) — двухуровневый: точное совпадение по
   `PatternYarn.yarnId`, затем fallback по толщине (`YarnRange`/`mPer100g`) и
   составу.
8. **Фото** — переиспользуем существующий пайплайн Pattern-изображений
   (multer + sharp thumbnailer + `ImageGalleryManager`), с отдельной
   upload-директорией под пряжу.
9. **Навигация — решено окончательно (было открытым вопросом, затем
   доуточнено под требование «для обычных пользователей на время ADMIN-only
   теста ничего не меняется»).** У мини-аппа сейчас нет нижнего таб-бара
   вообще (уточнено разбором кода: `App.tsx` рендерит только `<Routes>` без
   общей layout-обёртки; переход в «Избранное» сейчас сделан точечной
   кнопкой-иконкой в `SearchFilterBar` — общем компоненте для Catalog и
   Favorites). Строим новый нижний таб-бар с нуля, три пункта:
   **Описания** (текущий Catalog) / **Пряжа** (новое хранилище) /
   **Избранное** (текущий Favorites). Виден только на трёх главных
   экранах-разделах; скрыт на внутренних экранах (карточка описания,
   карточка пряжи, формы добавления/списания) — там навигация назад через
   обычную стрелку «Назад» в шапке, как сейчас.

   **Гейтинг таб-бара — критично, закрывает требование "без изменений для
   обычных пользователей".** Таб-бар целиком (не только пункт «Пряжа»)
   показывается ТОЛЬКО пользователям с доступом к хранилищу
   (`PREMIUM_YARN_STASH` или `ADMIN` — тот же принцип «роль ИЛИ разрешение»,
   что везде в проекте). У пользователя без доступа таб-бар не рендерится
   вообще — вместо него остаётся текущее поведение: точечная кнопка перехода
   в избранное в `SearchFilterBar`, как сейчас. Никакого «видимого, но
   заблокированного» пункта меню нет — на время ADMIN-only теста для всех
   остальных пользователей интерфейс визуально и функционально идентичен
   тому, что есть сегодня.

   **Механизм гейтинга — переиспользование существующего паттерна, не новая
   работа.** Разрешения на фронтенд приходят одним массивом в ответе
   `POST /auth/telegram` и читаются хуком
   `apps/frontend-miniapp/src/hooks/usePremiumAccess.ts` — там уже есть
   готовый пример точно такого же гейта для похожего разрешения:
   `yarns: isAdmin || permissions.includes("PREMIUM_YARNS")`. Для таб-бара
   добавляется аналогичное поле `yarnStash: isAdmin ||
   permissions.includes("PREMIUM_YARN_STASH")`, и слой, решающий рендерить
   таб-бар или старую кнопку, читает этот флаг.

   **Известное и принятое ограничение (тот же паттерн, что уже есть у всех
   остальных Permission-флагов в проекте):** разрешения читаются из кэша
   один раз при запуске мини-аппа, без поллинга и повторных запросов.
   Если админ выдаст пользователю `PREMIUM_YARN_STASH` во время активной
   сессии, тот увидит таб-бар только после следующего перезапуска
   мини-аппа — не мгновенно. Это не баг нового кода, а существующее
   поведение всего механизма permissions в проекте (`PREMIUM_YARNS` и
   остальные флаги ведут себя точно так же); чинить отдельно для этого
   флага не требуется. См. T18-T19 в Implementation Tasks.

## 2. Модель данных (миграция, аддитивная)

```prisma
enum Permission {
  MINI_APP
  AUTHOR_CABINET
  ADMIN
  PREMIUM_CORE
  PREMIUM_EXTRA
  PREMIUM_DETAILS
  WEB_ACCESS
  PRICE_ALERT
  PREMIUM_YARN_STASH   // + новое значение, чисто аддитивно
}

// Существующий enum (yarnsController.ts). Получает третье значение —
// см. §5.1: отклонённая личная заявка пользователя не удаляется больше,
// а помечается REJECTED, чтобы остаться видимой владельцу в его хранилище,
// но не предлагаться другим через suggestYarns/listYarns.
enum YarnStatus {
  PENDING
  APPROVED
  REJECTED   // + новое значение
}

// ─── Хранилище пряжи пользователя ─────────────────────────────────────────
// Один Yarn (артикул из справочника или PENDING-заявка пользователя) может
// быть представлен несколькими StashSkein — разный цвет/партия одной и той
// же пряжи (см. §3.1 YARN_ARTICLES_PLAN.md — та же логика "многие записи на
// один артикул", что там обоснована для PatternYarn, только в другую сторону:
// здесь много СВОИХ экземпляров на один справочный Yarn).
model StashSkein {
  id     String @id @default(uuid())
  userId String
  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  yarnId String
  yarn   Yarn   @relation(fields: [yarnId], references: [id])

  // Снимок полей Yarn на момент добавления — ВСЕГДА копируется при создании,
  // независимо от статуса артикула (APPROVED/PENDING). Один путь чтения для
  // всех карточек: экран хранилища всегда читает отсюда, никогда через
  // yarn.* напрямую. Если справочник потом уточнит данные (например, модератор
  // поправит метраж), в карточке пользователя останется снятое значение, пока
  // он сам не обновит его явным действием «обновить из справочника» — это
  // сознательный компромисс (актуальность вместо ветвления по Yarn.status,
  // см. обсуждение CEO review, cross-model finding #5).
  yarnNameSnapshot String
  brandSnapshot    String?
  mPer100gSnapshot Int?
  compositionSnapshot String?

  colorName   String?
  dyelot      String?  // партия/лот окраски — важно, оттенок одной и той же
                        // партии красителя отличается от партии к партии
  totalWeightG Int      // исходный вес на момент добавления
  currentWeightG Int    // текущий остаток — изменяется ТОЛЬКО атомарно вместе
                        // со вставкой/удалением соответствующей StashUsage в
                        // одной транзакции (см. §3 про UPDATE ... WHERE guard)
  note        String?
  images      String[] @default([])

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  swatches StashSwatch[]
  usages   StashUsage[]

  @@index([userId])
  @@index([yarnId])
}

// Отвязанный образец (свотч) — плотность и спицы конкретной вязки, не самого
// артикула (у одной и той же пряжи плотность гуляет в зависимости от спиц,
// натяжения вязальщицы). Несколько на один StashSkein.
model StashSwatch {
  id           String     @id @default(uuid())
  skeinId      String
  skein        StashSkein @relation(fields: [skeinId], references: [id], onDelete: Cascade)

  images         String[] @default([])
  needleSizeRaw  String?
  // Плотность ДО ВТО — тот же формат чисел, что у Pattern.densityStitches/Rows.
  densityStitchesBefore Decimal? @db.Decimal(5, 2)
  densityRowsBefore     Decimal? @db.Decimal(5, 2)
  // Плотность ПОСЛЕ ВТО.
  densityStitchesAfter  Decimal? @db.Decimal(5, 2)
  densityRowsAfter      Decimal? @db.Decimal(5, 2)

  createdAt DateTime @default(now())

  @@index([skeinId])
}

// Лог расхода запаса — append-only, по образцу PatternView/PaywallEvent.
// patternId опционален: пользователь может списать вес без указания, на что.
//
// КРИТИЧНО (найдено внешней проверкой плана против кода, до реализации):
// `pattern Pattern? @relation(...)` без `onDelete` — это RESTRICT по
// умолчанию в Prisma/Postgres. adminPatternsController.ts:460 уже сегодня
// делает `prisma.pattern.delete({ where: { id } })` — существующий,
// задеплоенный путь физического удаления архивных (`isVisible: false`)
// паттернов. Как только у паттерна появится хотя бы одна `StashUsage`,
// это удаление начнёт падать FK constraint violation → 500 в общем catch,
// вместо аккуратной ошибки. План изначально это не заметил (не покрыто
// «IRON RULE регрессии» §8, хотя должно было).
//
// Решение (по требованию пользователя): при удалении Pattern связь НЕ
// молча обнуляется (`SetNull`) — вместо этого `StashUsage` хранит
// СНИМОК данных описания на момент списания, чтобы пользователь не терял
// текстовый артефакт «на что я потратила эту пряжу» после того, как автор
// или админ уберут паттерн из каталога. patternId остаётся nullable-ссылкой
// (для перехода на живую карточку, пока она существует) СВЕРХУ снимка, не
// вместо него.
model StashUsage {
  id        String      @id @default(uuid())
  skeinId   String
  skein     StashSkein  @relation(fields: [skeinId], references: [id], onDelete: Cascade)
  amountG   Int         // положительное число — сколько списано

  // Живая ссылка — используется, пока Pattern существует (переход на
  // карточку из истории списаний). onDelete: SetNull — при удалении
  // паттерна это поле обнуляется, но снимок ниже остаётся.
  patternId String?
  pattern   Pattern?    @relation(fields: [patternId], references: [id], onDelete: SetNull)

  // Снимок — пишется ВСЕГДА в момент создания StashUsage, если patternId
  // указан (независимо от того, удалят ли Pattern потом). Переживает
  // удаление паттерна из каталога.
  patternTitleSnapshot  String?
  patternAuthorSnapshot String?

  // Опциональное фото готового изделия, загруженное пользователем в момент
  // списания — тот же upload-пайплайн, что у фото мотка/образца (§3.1).
  // Одно фото, не обязательно. Не связано с защитой от удаления Pattern
  // выше — это отдельная user-facing возможность внутри флоу списания
  // (см. §10, bottom sheet), не техническая заплатка.
  finishedPhotoUrl String?

  note      String?
  createdAt DateTime    @default(now())

  @@index([skeinId])
  @@index([patternId])
}
```

**Критично (закреплено на CEO review, cross-model finding #3/#4):** вставка
`StashUsage` и декремент/инкремент `StashSkein.currentWeightG` — ОДНА атомарная
операция в одной транзакции, не «прочитать баланс, потом два отдельных
запроса». Для списания — `UPDATE "StashSkein" SET "currentWeightG" =
"currentWeightG" - $amount WHERE id = $skeinId AND "currentWeightG" >=
$amount` (0 затронутых строк ⇒ 400, недостаточно пряжи) в одной транзакции с
`INSERT INTO "StashUsage"`. Для `DELETE /stash/usage/:id` (отмена списания) —
симметрично: `UPDATE ... SET "currentWeightG" = "currentWeightG" + $amount
WHERE id = $skeinId AND "currentWeightG" + $amount <= "totalWeightG"` в одной
транзакции с удалением строки `StashUsage` — без этого встречного ограничения
двойное срабатывание отмены (или отмена гонки с новым списанием) может увести
остаток выше исходного веса, что ломает инвариант, на котором стоит вся фича
учёта запаса.

Изменения в существующих моделях:
- `User.stashSkeins StashSkein[]` (обратная связь).
- `Yarn.stashSkeins StashSkein[]` (обратная связь) — не мешает существующей
  логике merge/reject: при `mergeYarn` и `rejectPendingYarn` нужно решить,
  что происходит с чужими `StashSkein.yarnId`, см. §5.
- `Pattern.stashUsages StashUsage[]` (обратная связь, опциональная).

`currentWeightG` денормализован (не считается на лету суммой `usages`) —
та же логика, что `Pattern.imageUrl`/`Pattern.popularityScore`: часто
читаемое поле не должно требовать агрегации при каждом открытии карточки.
Источник истины — `totalWeightG - Σ StashUsage.amountG`; списание делает обе
записи в одной транзакции.

## 3. Backend API (новый роутер `/stash`, по образцу `/author`)

```
router.use(requireAuth);
router.use(requirePermissionOrAdmin(Permission.PREMIUM_YARN_STASH));

GET    /stash/skeins                    — список артикулов пользователя, ПАГИНИРОВАННЫЙ (page/pageSize, тот же паттерн что listYarns)
POST   /stash/skeins                    — добавить моток/партию (yarnId ИЛИ данные для нового PENDING Yarn)
GET    /stash/skeins/:id                — карточка (включая swatches, usages, подбор описаний) [loadOwnedSkein]
PATCH  /stash/skeins/:id                — редактировать (цвет, партия, вес, фото, заметка) [loadOwnedSkein]
DELETE /stash/skeins/:id                — удалить свою запись [loadOwnedSkein]

POST   /stash/skeins/:id/usage          — списать расход { amountG, patternId?, note? } [loadOwnedSkein]
DELETE /stash/usage/:id                 — отменить ошибочное списание (возвращает currentWeightG) [loadOwnedSkein по skein усечённой usage]

POST   /stash/skeins/:id/swatches       — добавить образец [loadOwnedSkein]
PATCH  /stash/swatches/:id              — редактировать образец [loadOwnedSkein по родительскому skein]
DELETE /stash/swatches/:id              — удалить образец [loadOwnedSkein по родительскому skein]

GET    /stash/skeins/:id/matches        — подбор описаний (см. §4) [loadOwnedSkein]

GET    /stash/yarns/suggest             — переиспользует suggestYarns() as-is (поиск по мере ввода, только APPROVED)
POST   /stash/yarns                     — переиспользует createAuthorYarn() as-is, только под PREMIUM_YARN_STASH-гейтом вместо AUTHOR_CABINET
```

Все ручки — `requirePermissionOrAdmin(Permission.PREMIUM_YARN_STASH)`, тот же паттерн,
что уже гейтит `/author/*` через `AUTHOR_CABINET`
(`requirePermission.ts:38`). `POST /stash/yarns` и `GET /stash/yarns/suggest`
— **тонкие обёртки над существующими экспортами `yarnsController.ts`**, не
дублирование логики: `createAuthorYarn` уже не завязан на конкретное
разрешение вызывающего роута, только на `req.body`. При реализации нужно
обновить докстринг `createAuthorYarn` (`yarnsController.ts:186-192`), который
сейчас жёстко упоминает только `POST /author/yarns` — иначе комментарий
перестанет соответствовать действительности.

**Проверка владения — единый middleware (закреплено на CEO review, finding
#3, Security).** Не полагаемся на дисциплину «каждый хендлер обязан
проверить» — заводим `loadOwnedSkein` (по аналогии с уже существующими
паттернами загрузки владения в кодовой базе), который для каждого
`:id`-роута делает `WHERE id = :id AND userId = req.user.userId`, кладёт
результат в `req.skein` и при отсутствии совпадения возвращает **404**, не
403 — чтобы не подтверждать существование чужого id открытым текстом.
`ADMIN` обходит эту проверку (видит любую запись) — тот же принцип, что у
`requirePermissionOrAdmin`. Для роутов, оперирующих `StashSwatch`/`StashUsage`
по их собственному `:id`, `loadOwnedSkein`-эквивалент подгружает запись через
родительский `skeinId` и проверяет владение транзитивно.

### 3.1. Загрузка фото

Новая директория `uploads/yarn-stash/` (по аналогии с `uploads/patterns/`).
Два пути на выбор:
- (а) параметризовать существующий `imagePipeline.ts`/`patternImages.ts` по
  `resolveDir`/upload-префиксу и завести отдельный `POST /stash/upload`,
  либо
- (б) переиспользовать `/admin/upload` как общий "images bucket".

**Выбрано: (а).** Обоснование варианта (б) как «проще» в исходном тексте
плана было неточным — **уточнено внешней проверкой плана против кода:**
`/admin/upload` (`apps/backend/src/routes/admin.ts:145`) жёстко гейтится
`requirePermissionOrAdmin(Permission.AUTHOR_CABINET)` — пользователь с
`PREMIUM_YARN_STASH`, но без `AUTHOR_CABINET`, получил бы 403. То есть

## 4. Подбор описаний («что можно связать») — v1

Реализуется в `GET /stash/skeins/:id/matches`, без отдельной таблицы —
чистое чтение (переиспользует существующие данные каталога, ничего не пишет):

**Финальная логика (уточнена после отдельного анализа допусков, заменяет
все более ранние черновые формулировки этого раздела).** Совпадение по ЛЮБОМУ
из трёх независимых критериев — не последовательный fallback «сначала A,
если пусто — B», а объединение результатов всех трёх:

1. **Точное совпадение по артикулу** — `Pattern` через
   `PatternYarn.yarnId = skein.yarnId` (или через `mergedIntoId`, если
   справочная карточка была слита после того, как пользователь её выбрал —
   см. §5). **Уточнено внешней проверкой плана против кода:** текущий код
   резолвит `mergedIntoId` только single-hop (`?? id`, без рекурсии) —
   `mergeYarn` не проверяет, что `targetId` сам не является уже слитой
   карточкой (`yarnsController.ts:241-245`), то есть цепочки из двух и более
   слияний уже потенциально возможны в существующих данных сегодня,
   независимо от этого плана. План не даёт готовой утилиты резолва цепочки —
   если она понадобится для `matches`, это новая работа, а не
   переиспользование существующей логики.

2. **Совпадение по толщине нити, допуск ±8%** (не абсолютное число метров).
   **Обоснование допуска (анализ проведён отдельно):** фактические диапазоны
   `YarnRange` в каталоге растут вместе с толщиной (0-250 / 251-350 /
   351-500 / 501-700 / 701+ м/100г, откалиброваны под реальное распределение
   пряжи в каталоге — см. `apps/backend/scripts/seed-yarn-ranges.ts`).
   Фиксированное число (например ±20 м) даёт разную относительную точность
   на разных концах шкалы: ±20 от 250 м — это ±8%, а ±20 от 50 м (толстая
   зимняя пряжа) — уже ±40%, что стирает разницу между категориями толщины.
   Процентный допуск масштабируется вместе с толщиной и даёт одинаково
   осмысленный результат на всём диапазоне. Реализуется как
   `Pattern.yarnRanges` пересекается с диапазоном
   `[skein.yarn.mPer100g × 0.92, skein.yarn.mPer100g × 1.08]` — **новая
   логика, не переиспользование существующего фильтра каталога**
   (`patternsController.ts:272-298` сопоставляет `yarnRanges` по `id`,
   который пользователь уже выбрал чекбоксом в UI, а не вычисляет диапазон
   из сырого числа — см. T14 в Implementation Tasks).

3. **Совпадение по плотности отвязанного образца ПОСЛЕ ВТО, допуск ±1
   петля / ±1 ряд** (фиксированное число, не процент). **Обоснование:** в
   отличие от метров (широкий диапазон 30-800), плотность на 10×10 см —
   счётное целое число с естественным масштабом: 1 петля — это всегда
   одинаково заметная для вязальщицы разница независимо от толщины пряжи
   (плотность толстой пряжи ~10 петель, тонкой ~30+; ±1 петля значит разное
   в процентах на разных концах шкалы, но воспринимается одинаково — это
   реальная единица счёта петель, не абстрактный процент). Сравнивается
   `StashSwatch.densityStitchesAfter`/`densityRowsAfter` с
   `Pattern.densityStitches`/`densityRows`.

**Состав (`composition`) сознательно НЕ участвует в подборе v1.** Текстовое
сравнение строк ненадёжно (разный порядок слов, синонимы вроде
«акрил»/«акриловое волокно» — см. опыт разбора состава в
`YARN_ARTICLES_PLAN.md` §0.3d, где для этого потребовался отдельный словарь
и нормализация). Пока такого словаря нет, добавление состава в подбор дало
бы ложную точность. Состав остаётся видимым пользователю в карточке пряжи,
просто не участвует в автоматическом сопоставлении. Это решение, а не
временный пробел — пересмотр требует отдельного анализа словаря синонимов,
вне объёма этого плана.

Результаты трёх путей объединяются (один и тот же `Pattern` не дублируется,
если подошёл сразу по нескольким критериям). UI для случая "совпадений не
нашлось" обязателен независимо от порогов — пустой список без объяснения
недопустим (см. §9, Pass 2).

## 5. Открытые вопросы / зоны риска для eng-review

1. **Что происходит со `StashSkein.yarnId`, когда справочный `Yarn`
   сливается (`mergeYarn`) или отклоняется (`rejectPendingYarn`)? — уточнено
   и переписано на eng review после разбора реального бизнес-сценария
   с пользователем.**

   Реальная логика модерации личных заявок пользователя (не автора — этот
   же путь для авторских PENDING-заявок не меняется, там `StashSkein` не
   участвует):

   - **Одобрено как есть** (`approveYarn`, без правок) — артикул становится
     `APPROVED`, попадает в общий справочник, у пользователя всё как было.
   - **Одобрено с правками** (админ сначала `updateYarn`, потом
     `approveYarn`) — артикул в общем справочнике получает исправленные
     поля. У пользователя в его `StashSkein` ничего не меняется: карточка
     хранилища читает `*Snapshot`-поля (см. §2), снятые в момент, когда он
     сам вводил данные — «тихой» подмены нет, что и требовалось.
   - **Отклонено** (`rejectPendingYarn`) — артикул НЕ попадает в общий
     справочник, но должен остаться у пользователя как его личная запись.
     **Меняет поведение существующей функции**: сейчас `rejectPendingYarn`
     физически удаляет строку `Yarn` (`yarnsController.ts:323-333`) — это
     несовместимо с требованием «пряжа остаётся у добавившего». Решение:
     новый статус `YarnStatus.REJECTED` (третье значение enum, наравне с
     `PENDING`/`APPROVED`). `rejectPendingYarn` вместо удаления ставит
     `status: REJECTED` (по аналогии с тем, как `mergeYarn` уже ставит
     `isActive: false` вместо удаления — `yarnsController.ts:282`).
     `REJECTED`-карточки не показываются в `suggestYarns`/`listYarns` по
     умолчанию (те уже фильтруют по `status: APPROVED`/`isActive: true`,
     `REJECTED` просто никогда не попадает в эти фильтры — доп. изменений
     в существующих ручках поиска не требуется) и не предлагаются другим
     пользователям, но `StashSkein.yarnId` продолжает ссылаться на неё как
     ни в чём не бывало — владелец видит свою карточку без изменений.
     `PatternYarn`/`PatternYarnMention`/`DraftYarn` очистка, которую сейчас
     делает `rejectPendingYarn` при удалении, больше не нужна для
     `REJECTED`-пути с существующими `StashSkein`-ссылками (тем более что
     `PatternYarn`/`DraftYarn` у личных, не прошедших модерацию заявок и
     не возникает — эти связи появляются только у `APPROVED` артикулов).
   - **Слито с дублем в справочнике** (`mergeYarn`) — по словам
     пользователя, эта функция существует ИСКЛЮЧИТЕЛЬНО для схлопывания
     дублей одного и того же артикула в общем справочнике (опечатки,
     повторный ввод), а не для объединения разной, но похожей пряжи —
     сценарий «слили две РАЗНЫЕ пряжи, и связь пользователя стала неверной»
     не рассматривается как реальный (и вне scope этого плана — если он
     когда-то возникнет, это баг использования `mergeYarn`, а не хранилища).
     В рамках этого понимания перенос `StashSkein.yarnId` на `targetId`
     при слиянии — простое и безопасно корректное поведение: пользователь
     как добавлял «свою» пряжу, так и продолжает её видеть, просто теперь
     она указывает на объединённую (уже единственно правильную) карточку
     справочника. **Уточнено внешней проверкой плана против кода:** в
     отличие от `PatternYarn` (перенос которого требует сырого SQL из-за
     уникального индекса `(patternId, yarnId)`), у `StashSkein.yarnId`
     сознательно НЕТ уникального индекса (§1.4 — один пользователь может
     иметь несколько записей на один и тот же артикул, разные цвет/партия)
     — перенос при merge делается простым `prisma.stashSkein.updateMany({
     where: { yarnId: id }, data: { yarnId: targetId } })`, без риска
     конфликта уникальности и без сырого SQL. Сравнение с переносом
     `PatternYarn` в исходном тексте плана было неточным.

   **Дополнительно к миграции схемы:** `YarnStatus` получает третье
   значение `REJECTED`. **Критично — найдено внешней проверкой плана
   против кода, до реализации:** утверждение «`deleteYarn` по-прежнему
   блокируется 409 при наличии `StashSkein`-ссылок — это НЕ меняется» было
   ФАКТИЧЕСКИ НЕВЕРНЫМ на момент написания — такой защиты не существует,
   потому что `StashSkein` ещё не создан. Текущий `deleteYarn`
   (`yarnsController.ts:337-356`) считает только `patternLinks` (count по
   `PatternYarn`) и `draftLinks` (count по `DraftYarn`) вручную — именно
   потому, что голый FK без явной проверки в Prisma даёt либо неаккуратную
   ошибку 500, либо (если миграция сгенерирует не-RESTRICT default) тихое
   удаление артикула, на который ссылается чужое хранилище. Обязательная
   задача при реализации (не покрыта T1-T13 изначально, добавлена как T15):
   `deleteYarn` должен дополнительно считать `prisma.stashSkein.count({
   where: { yarnId: id } })` в общей сумме `links`, точно по той же схеме,
   что уже сделано для `patternLinks`/`draftLinks`.

   **Проверено, где ещё `Yarn.status` фильтруется** (`yarnsController.ts`):
   `suggestYarns` (:125) уже фильтрует строго `APPROVED` — `REJECTED`
   автоматически не попадёт в публичный поиск-подсказку для других
   пользователей, доп. правок не требуется. `listYarns` (:40, админский
   список) намеренно НЕ фильтрует по статусу — админ должен видеть
   `REJECTED`-карточки наравне с остальными для аудита, это корректно как
   есть. Пред-существующая (не вызванная этим планом) непоследовательность:
   `listYarnBrands`/`listYarnLines` (:74, :92) не фильтруют по статусу
   вовсе — `PENDING`/`REJECTED` бренды уже сегодня протекают в автокомплит
   бренда/линейки при создании ДРУГИХ артикулов. Не регрессия этого плана,
   отдельная задача вне объёма.

2. **`PREMIUM_YARN_STASH` — режим запуска (закреплено на CEO review).** В
   отличие от `PREMIUM_CORE` (выдан всем бесплатно, платность включена позже),

   истории бесплатного использования — нет пользователей, у которых что-то
   отбирают при включении платности.

10. **ADMIN-bypass в `loadOwnedSkein` — решено на eng review.** Веб-поиск
    подсветил известный класс бага: если `req.user.role` не заполнен (напр.
    токен выпущен без role в payload), проверка `role === ADMIN` тихо
    проваливается и админ теряет доступ к чужим записям без ошибки в логах —
    "выглядит корректно", но сломано. Обязательное требование: `loadOwnedSkein`
    читает роль тем же путём, что уже проверенный `requirePermissionOrAdmin`
    (из БД/сессии, а не напрямую из некопроверенного `req.user`), и в набор
    тестов (см. §8, Test Review) ОБЯЗАТЕЛЬНО входит явный кейс «ADMIN видит
    чужую запись» — не только «обычный пользователь не видит чужую».

11. **Отсутствие тестовой инфраструктуры в проекте — зафиксировано на eng
    review.** Во всём `apps/backend` нет ни одного тестового фреймворка, ни
    одного файла тестов — это предшествующее состояние проекта, не вызвано
    этим планом, и настройка тестового фреймворка — отдельная задача вне
    объёма. Поскольку `mergeYarn`/`rejectPendingYarn` — уже существующие,
    задеплоенные функции, которые этот план расширяет, регрессионный риск
    реален независимо от наличия автотестов. Закрыто через обязательный
    ручной QA-чеклист перед первым деплоем (см. §8 ниже) — не автотест, но
    формальный, обязательный шаг, а не «полагаемся на то, что не сломается».

12. **Оптимизация чтения — решено на eng review.** Благодаря
    `*Snapshot`-полям (пункт 1 выше), `GET /stash/skeins` (список) и
    `GET /stash/skeins/:id` (карточка) читают ТОЛЬКО `StashSkein` (плюс
    `swatches`/`usages` через `include` для карточки) — JOIN с `Yarn` НЕ
    нужен для отображения ни в одном из этих двух эндпоинтов. Единственное
    место, где нужен реальный (не снятый) join с `Yarn` — `GET
    /stash/skeins/:id/matches`, потому что подбору нужны live
    `PatternYarn`/`mPer100g` ЦЕЛЕВОГО (актуального после возможного merge)
    артикула, а не снимок на момент добавления в хранилище.

## 10. Design review — флоу «Списать пряжу» (второй проход plan-design-review)

Отдельное ревью для формы списания, которой не было в макетах на момент §9.
`gstack designer` (AI-генератор мокапов) недоступен в этом окружении (нет
OpenAI API ключа) — макет спроектирован и собран напрямую в Figma-копии
пользователя через `use_figma`, из уже существующих компонентов хранилища
(`InputField`, `Icon/checkbox`, `Button/Regular`, `CategoryChip`), тем же
способом, что и объединение модалки добавления в §9.

**Обсуждение с пользователем.** Исходное предложение — 3 отдельных шага
(1. выбрать описание → 2. ввести граммовку → 3. подтверждение). Пересмотрено
на 2 шага: сначала обязательное (сумма списания), потом опциональное
уточнение (связь с описанием) — потому что связь с `Pattern` опциональна по
плану (§2, `StashUsage.patternId?`), а сумма обязательна всегда. Отдельный
шаг подтверждения убран — экран ввода суммы уже показывает результат
("Останется: X г из Y г") прямым текстом, дублирующее окно "точно?" не несёт
новой информации и было бы чистым трением (Krug: лишний клик без причины
думать не бесплатен).

**Формат экрана — bottom sheet** (шторка снизу, карточка пряжи видна сзади),
не полноценный экран как модалка добавления: списание — быстрое
второстепенное действие относительно контекста карточки, а не отдельная
задача навигации.

**Собранный макет** (в Figma-копии, узел `Списать пряжу (bottom sheet)`,
`node-id=3010:7112`):
1. Заголовок "Списать пряжу" + drag handle сверху.
2. **Обязательное поле** "Сколько граммов списать*" (переиспользован
   компонент `InputField`).
3. **Живой пересчёт остатка** под полем — "Останется: 20 г из 750 г",
   обновляется по мере ввода (закрывает Pass 2, живая валидация ошибки
   перерасхода: если введённое > текущего остатка, тот же текст должен
   переключаться на предупреждение до отправки формы, не после).
4. **Чекбокс "Списать весь остаток (20 г)"** — переиспользован существующий
   компонент `Icon/checkbox` (`46:3049`), уже используемый в проекте.
5. **Опциональный блок** "Связать с описанием (необязательно)" —
   переиспользован паттерн `CategoryChip` (та же пунктирная рамка, что у
   "Добавить фото"/"Добавить образец" в остальных макетах хранилища).

   **Детальный путь внутри блока (уточнено по запросу пользователя, ниже
   заменяет прежнюю расплывчатую формулировку "поиск + карточки"):**
   1. Пользователь нажимает на чип "Связать с описанием (необязательно)" —
      блок раскрывается.
   2. **Сразу**, до какого-либо ввода, показывается подборка «Что можно
      связать» — те же карточки, что уже выводятся на карточке пряжи (§9),
      результат `GET /stash/skeins/:id/matches` (§4: точный артикул ИЛИ
      толщина ±8% ИЛИ плотность образца ±1 петля/ряд). Это экономит
      пользователю набор текста в частом случае — пряжа обычно уже
      «известна» каталогу.
   3. Над подборкой — поле поиска (то же самое `GET /patterns?search=`,
      что использует обычный каталог — переиспользуется без изменений,
      debounce ~300мс, как в `Catalog.tsx`), на случай если нужного
      описания нет в подборке «что можно связать» (например, пользователь
      вязал что-то без точного совпадения по параметрам).
   4. Каждая карточка результата (что из подборки, что из поиска) кликабельна
      целиком — один тап выбирает её. Выбранная карточка визуально
      выделяется (например, рамкой цвета `#bec1f4`), блок можно свернуть
      обратно, показывая имя выбранного описания вместо самого чипа.
   5. **К одному списанию можно привязать только одно описание** — повторный
      выбор другой карточки заменяет предыдущий выбор, не добавляет
      второй. Совпадает с текущей схемой (`StashUsage.patternId` — одно
      значение, не массив).
   6. Пустой результат поиска (запрос не дал совпадений) — текст "Ничего не
      найдено" + кнопка "Пропустить" (не блокирует списание — связь с
      описанием необязательна с самого начала, см. §2).
   7. Нажатие "Готово" на всей форме списания сохраняет выбранное описание
      вместе с суммой — отдельного шага подтверждения выбора описания нет
      (согласуется с решением из Pass 3 §10 не дублировать подтверждение).
6. **Опциональное фото готового изделия** (добавлено после обсуждения findings
   от внешней проверки плана против кода, см. §1/§5.1 finding 1) — одно
   опциональное фото, тот же `CategoryChip`-паттерн загрузки, что у фото
   мотка/образца. Записывается в `StashUsage.finishedPhotoUrl` (T17).
7. Кнопка **"Готово"** снизу (переиспользован стиль primary-кнопки
   `#bec1f4`, тот же, что "Списать пряжу"/"Сохранить" в остальных экранах).
