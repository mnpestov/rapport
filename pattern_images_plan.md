# Множественные изображения у описаний — план реализации

Статус: план согласован, код не написан.

## 1. Текущее состояние

Одна картинка хранится независимо в трёх местах:

- `Pattern.imageUrl` — колонка в схеме, обязательная (`NOT NULL`)
- `Draft.imageUrl` — черновик автора в кабинете, тоже колонка в схеме
- `AuthorSyncItem.parsedData.imageUrl` — JSON-поле новинки от скрапера

Копируется 1:1 при переходе между сущностями:
- `authorController.ts::createEditDraft` (~строка 225-234) — `Pattern → Draft`, копирует `imageUrl: pattern.imageUrl`
- `adminController.ts::approveDraft` — `Draft → Pattern`
- `syncController.ts::processSyncBatch` (~строка 112-114) — `AuthorSyncItem → Pattern`, жёстко читает `parsedData?.imageUrl`, бросает `"No image URL"` если поля нет

### Кто отображает картинку

Не требует изменений (везде нужна ровно одна — обложка):
- Мини-апп: карточка каталога (`PatternCard`)
- Админка: `PatternCard`, `PatternGridCard`, `ModerationCard` — везде только превью-миниатюра

Требует изменений:
- Мини-апп: `PatternDetails.tsx` — единственное место с реальной потребностью в галерее (сейчас один `<img>` с кнопкой избранного поверх)
- Админка: модалка редактирования в `Patterns.tsx` (общая для admin/author через `variant`) и `SyncItemEditModal.tsx` — сейчас используют одиночный `ImageCropper` (выбор файла → обрезка 4:5 → загрузка → один url)

### Загрузка / хранение

- `POST /admin/upload` — универсальный, один файл за раз, легко дёргать N раз без изменений эндпоинта
- Ручная загрузка → `/uploads/patterns/`, скачанное скрапером → `/images/patterns/` (два разных каталога, уже так сегодня)

### Скрапер (`author_sync.py`)

- Tilda Store сайты (kitirrr, tsinbal, knithappens, lenakotikova, lavkabulavka): API уже отдаёт полную галерею — `gallery` в JSON-ответе содержит несколько фото. `_tilda_store_image()` сейчас берёт только `gallery[0]`, остальное отбрасывает. Расширение почти тривиально.
- Generic-краулер (все остальные сайты): на странице каталога видна только одна превью-картинка на товар; чтобы получить остальные, нужно заходить на страницу товара и парсить галерею — вёрстка у каждого сайта своя, единого паттерна нет. **В этот заход не трогаем**, добавляем точечно по мере репортов по конкретным авторам (как весь этот проект добавлялись сайт-специфичные фиксы `parse_yarn`/`parse_density`).

## 2. Модель данных (согласовано)

- **`images: String[]`** — единственный источник правды, от 1 до 5 фото, порядок = порядок в массиве, первый элемент = обложка.
- **`imageUrl`** — остаётся колонкой (нужна всем местам с «ровно одна картинка»), но становится *вычисляемым* значением: бэкенд на каждую запись сам выставляет `imageUrl = images[0]`. Ни админ, ни автор не редактируют его напрямую.
- То же самое для `AuthorSyncItem.parsedData`: пишем `images: string[]`, `imageUrl` вычисляется в момент создания `Pattern` при одобрении.

Такая схема решает задачу «сделать другое фото обложкой» без отдельной кнопки — просто переставить фото на первое место (drag-and-drop) и сохранить.

### Зафиксированные решения (из обсуждения)

- Галерея нужна и в кабинете автора, не только в админке — `Draft` тоже получает `images`.
- Максимум **5** фото на описание.
- Перестановка местами — **drag-and-drop** уже в первой версии, нативный HTML5 DnD (`draggable`/`dragover`/`drop`), без новой библиотеки — в проекте сейчас нет DnD-зависимостей, а для плоской сетки из ≤5 элементов этого достаточно.
  - Проверено: кабинет автора — обычная веб-страница в `apps/admin` (вход по коду в Telegram, без Telegram WebApp SDK, это не Mini App/WebView), и во всём `apps/admin` сейчас **ноль** `@media`-запросов — админка и кабинет сегодня не адаптированы под тач вообще. Нативный DnD не создаёт регресса относительно текущего состояния. Если кабинет когда-нибудь станет мобильным — DnD-часть придётся переделать отдельно.

## 3. Найденные риски и как они закрываются

Полный список конкретных дыр, найденных при инженерном ревью плана, и точные фиксы:

1. **`processSyncBatch` упадёт для не-Tilda авторов.** Generic-краулер продолжит писать только `imageUrl` (singular), а не `images[]`. Нужен fallback везде, где читается `parsedData` с картинками:
   `images = parsedData.images ?? (parsedData.imageUrl ? [parsedData.imageUrl] : [])`
   Применяется в **трёх** местах: `processSyncBatch` (скачивание файлов), `updateSyncItem` (чтение текущего `parsedData` перед выдачей в форму редактирования), `SyncModal.tsx::toDraft()` (маппинг для отображения карточки новинки).

2. **Уже накопленные PENDING-элементы очереди в старом формате.** Тот же fallback из п.1 автоматически решает и это — элементы, созданные скрапером до деплоя, имеют только `imageUrl` и подхватятся той же логикой.

3. **`Pattern → Draft` теряет галерею.** `createEditDraft` должен копировать `images: pattern.images` рядом с `imageUrl: pattern.imageUrl` — иначе редактирование опубликованного описания автором покажет только обложку, а при аппруве такого черновика галерея живого паттерна обнулится.

4. **Обязательность фото.** Все проверки вида `if (!imageUrl)` переписываются на «`images` непустой»:
   - `authorController.ts::createDraft` (~строка 133)
   - `adminController.ts::createPattern`
   Дополнительно: на update-путях (`updateDraft`, `updatePattern`, `updateSyncItem`) нужно явно запретить `images: []` — частичное обновление сейчас не проверяет, что результат не станет пустым массивом.

5. **Бэкофилл при миграции.** Не просто `@default([])` — в той же миграции, что добавляет колонку `images`, сразу бэкофиллить существующие строки: `UPDATE "Pattern" SET images = ARRAY[imageUrl]` (и то же для `Draft`). Без этого вся существующая база показывает пустую галерею на `PatternDetails.tsx` до первого ручного пересохранения через новую форму.

6. **Единый хелпер вместо пересчёта в 5+ местах.** Общий модуль (например `apps/backend/src/utils/patternImages.ts`):
   - `deriveImageUrl(images)` → `images[0]`
   - `validateImages(images, { max: 5 })` → бросает ошибку/400 при пустом массиве или `length > 5`
   Все точки записи (`createPattern`, `updatePattern`, `createDraft`, `updateDraft`, `updateSyncItem`) обязаны идти через эти функции, а не реализовывать логику заново. Скрапер на Python — отдельный рантайм, хелпер туда не переносится; лимит применяется на стороне TS в момент записи в БД.

7. **Жёсткая валидация вместо тихой обрезки.** Разделение по типу источника:
   - Человеко-инициированные пути (`createPattern`, `updatePattern`, `createDraft`, `updateDraft`, `updateSyncItem`) — `validateImages` возвращает **400**, если пришло больше 5. На фронте кнопка «добавить фото» дизейблится по достижении 5 — и в общей форме `Patterns.tsx`, и в `SyncItemEditModal.tsx`.
   - `processSyncBatch` (машинное одобрение уже лежащих в очереди сырых данных скрапера) — единственное место с защитным `clamp` до 5 без 400: там нет «текущего запроса», который можно отклонить, а админ уже видел/мог подрезать фото через «Редактировать» до нажатия «В архив».

8. **Каталог получит `images[]` бесплатно и незаметно.** `patternsController.ts::getPatterns` (~строка 86-99) делает `findMany({ include: {...} })` без `select` — новая колонка автоматически попадёт в каждый ответ листинга каталога (до 5 URL × N паттернов на странице), хотя карточка использует только `imageUrl`. Нужен явный `select`/`omit`, исключающий `images` из ответа каталога.

9. **Touch для drag-and-drop.** См. раздел «Зафиксированные решения» выше — проверено и осознанно принято.

10. **Валидация URL в `images[]` — уточнено после повторного ревью.** Текущий `imageUrl` уже принимается без проверки origin (`authorController.ts` ~строка 300, существующая дыра, не создана этим планом) — при расширении в массив стоит закрыть заодно, но с поправкой:

    Первая версия правила («каждый URL обязан начинаться с `/uploads/patterns/`») конфликтует с бэкофиллом из риска №5: паттерны, изначально одобренные через скрапер, после бэкофилла содержат `/images/patterns/...` (подтверждено — `syncController.ts:151` пишет именно этот префикс; ручная загрузка через `admin.ts:117` — `/uploads/patterns/`). Оба префикса легитимны для разных паттернов уже сегодня. Единое правило «только `/uploads/patterns/`» сделало бы **любое** сохранение формы для скрапленного паттерна невозможным, даже если фото никто не трогал.

    Правило разделяется по операции:
    - **Создание** (`createPattern`, `createDraft`) — конфликта нет: новый паттерн/черновик всегда создаётся человеком через форму, легаси-фото взяться неоткуда. Каждый URL в `images[]` обязан начинаться с `/uploads/patterns/`.
    - **Обновление** (`updatePattern`, `updateDraft`, `updateSyncItem`) — валидация построена на диффе, а не на плоском правиле: элементы, которые совпадают с уже сохранённым в БД `images[]` этого паттерна/черновика (не изменились), пропускаются независимо от префикса — это legacy-фото, которые ничего не нарушают. Только **новые** элементы (присутствуют в запросе, отсутствовали в сохранённой версии) обязаны начинаться с `/uploads/patterns/`. Для диффа нужно прочитать текущий `images[]` строки до валидации запроса.
    - Данные скрапера в PENDING-очереди — произвольный `http(s)` с сайта автора допустим (это ожидаемо, ещё не наша копия); на одобрении (`processSyncBatch`) картинки скачиваются и подменяются на локальные `/images/patterns/...`, как и сегодня, просто для всех URL в массиве.

11. **Очистка осиротевших файлов с диска не была перенесена на массив.** У одиночной картинки сегодня есть логика удаления старого файла при замене/удалении паттерна — затрагивает три места: в двух логика уже есть и её нужно расширить на массив, в третьем логики нет и сегодня (не в скоупе):
    - `adminController.ts::updatePattern` (~строка 563-575) — при замене `imageUrl` удаляет старый файл, если он начинался с `/uploads/`
    - `adminController.ts::deletePattern`, ветка hard-delete архивного паттерна (~строка 679-689) — удаляет файл `existing.imageUrl`, если начинался с `/uploads/`
    - `authorController.ts` (Draft) — такой логики нет и сегодня; это существующий, не создаваемый этим планом пробел, вне скоупа

    Оба места переписываются на дифф массивов вместо сравнения одной строки: `removed = existingImages.filter(url => !newImages.includes(url))`, затем для каждого `url` из `removed`, начинающегося с `/uploads/`, — `unlink`. Без этого шага каждое удаление/замена фото в галерее будет копить файлы на диске вместо очистки, как это происходит сейчас для одной картинки. Оба места используют один и тот же дифф, который также нужен для риска №10 (обновление) — реализуются одним и тем же кодом.

## 4. Этапы реализации

### Этап 1 — схема
- `Pattern.images String[] @default([])`, `Draft.images String[] @default([])`
- Миграция с бэкофиллом (см. риск №5)

### Этап 2 — бэкенд
- Общий хелпер `deriveImageUrl` / `validateImages` (риск №6), плюс общая функция диффа `diffImages(existing, incoming)` → `{ added, removed }`, используемая и для origin-валидации на update (риск №10), и для очистки файлов (риск №11)
- `adminController.ts`: `getPatternById` (включить `images`), `createPattern` (принять `images`, строгая `/uploads/patterns/`-валидация, валидировать через `validateImages`, пересчитать `imageUrl`), `updatePattern` (то же + дифф-валидация origin только для новых элементов + unlink удалённых `/uploads/`-файлов), `deletePattern` hard-delete ветка (unlink всех `images`, начинающихся с `/uploads/`, не только бывшего `imageUrl`), `approveDraft` (перенести `draft.images` → `Pattern`)
- `authorController.ts`: `createDraft` (риски №4, №10-create), `updateDraft` (риски №4, №10-update — дифф), `createEditDraft` (риск №3)
- `syncController.ts`: `updateSyncItem` (принять `images`, legacy-fallback — риски №1/2), `processSyncBatch` (скачать все файлы из `images`, legacy-fallback, defensive clamp — риски №1, №7)
- `patternsController.ts`: `getPatternById` — включить `images` в публичный ответ; `getPatterns` — явно исключить `images` (риск №8)

### Этап 3 — админка
- `Patterns.tsx` (общая форма admin/author) и `SyncItemEditModal.tsx`: менеджер галереи вместо одиночного `ImageCropper` — сетка миниатюр (макс. 5), крестик на каждой для удаления, кнопка «добавить фото» (дизейблится на 5-м, переиспользует существующий crop-flow), нативный HTML5 drag-and-drop для перестановки
- `SyncModal.tsx::toDraft()` — legacy-fallback для отображения (риск №1/2)

### Этап 4 — мини-апп
- `PatternDetails.tsx`: горизонтальная карусель на всю ширину (свайп + точки-индикатор) на чистом CSS scroll-snap, без новых зависимостей
- Каталог не меняется — всегда только `imageUrl`

### Этап 5 — скрапер
- `_tilda_store_image()` → `_tilda_store_images()`, забирать весь `gallery[]` вместо `gallery[0]` — для kitirrr, tsinbal, knithappens, lenakotikova, lavkabulavka
- Generic-краулер не трогаем в этот заход (см. раздел 1)
