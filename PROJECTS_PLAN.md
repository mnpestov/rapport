# Вязальные проекты — план (v1, черновик)

Документ только для планирования. Кода не меняет. Задача: спроектировать
новую вкладку мини-аппа «Проекты» — личный трекер вязальных проектов
пользователя, объединяющий каталог описаний, личное хранилище пряжи
(`StashSkein`) и образцы плотности в одну карточку конкретного вязания.

Собрано на основе разбора макетов Figma (node-id=3029:7130 — исходный
фрейм со всеми экранами; node-id=3039:31704 и 3039:32158 — обновлённая
форма создания/карточка с блоками «Описание, файл» и «Референс», файл
`acvPfl8v8JqeAqfVvsViYY`) и текущего кода: `apps/backend/prisma/schema.prisma`
(модели `StashSkein`, `StashSwatch`, `StashUsage`, `Yarn`, `Pattern`,
`Instrument`), `stashController.ts` (`createSwatch`/`updateSwatch`,
`getMatches`, `suggestYarns`/Ravelry fallback), фронтовых
`AddSwatchModal.tsx`/`EditSwatchModal.tsx`/`StashSkeinDetails.tsx`,
`LogUsageWizard.tsx`.

Помимо трекера проектов как такового, план включает загрузку PDF-описаний
с выделением текста цветом внутри мини-аппа (§8) — добавлено в макет уже

## 0. Описание функциональности (согласовано с пользователем)

### Назначение

Личный трекер вязальных проектов. В перспективе — база для публичного
«портфолио» (см. §0.6 «Вероятные этапы развития») — это и объясняет
требование поддерживать создание уже завершённых проектов задним числом.

### 0.1. Список проектов (главный экран вкладки)

- Счётчик «Всего проектов: N», поиск по названию.
- Табы-фильтр по статусу: **В процессе** / **Завершён** / **Пауза**
  (с числом найденного при активном фильтре).
- Кнопка «Добавить проект» — **единственная** точка входа в создание (в
  макетах нет кнопок «Начать проект» на карточке описания/мотка).
- Сетка карточек 2 в ряд: фото/плейсхолдер, бейдж статуса, название, размер
  спиц.
- Пустое состояние — призыв создать первый проект.

### 0.2. Создание проекта — одна длинная форма (не пошаговый визард)

Обязательны только: **Название, Статус, Дата начала** (по умолчанию —
сегодня). Всё остальное опционально, можно дозаполнить позже через карточку
проекта.

- **Описание** — поиск по каталогу (название/автор).
  - Найдено → выбор привязывает `Pattern`; автор паттерна показывается
    автоматически; можно выбрать **более одного** паттерна на проект (или ни
    одного — привязка не обязательна никогда).
  - Не найдено → «Добавить вручную»: поле над «Описание» превращается в
    свободный ввод **Автора**, «Описание» — в свободное название/тему
    проекта, без привязки к `Pattern`.
- **Статус** — В процессе / Завершён / Пауза, выбирается сразу при создании.
- **Инструмент** — чекбоксы Спицы/Крючок (переиспользует существующую
  модель `Instrument`, см. §1.1). Предзаполняются из выбранного паттерна, но
  всегда редактируемы вручную.
- **Пряжа** — поиск и выбор одного или нескольких мотков из личного
  хранилища (`StashSkein`).
  - Если в хранилище не найдено — доступен переход к общему справочнику
    (`Yarn`); выбор оттуда сразу создаёт новый `StashSkein` (с вводом
    веса/остатка на месте, чтобы новый моток был осмысленным), который сразу
    привязывается к проекту.
  - Поле **«Расход»** по мотку показывается **только когда `Project.status
    == COMPLETED`** — ни при «В процессе», ни при «Пауза» поля «Расход» в
    форме нет вообще (см. §0.3 про модель списания).
- **Образец** — **отдельная сущность**, привязанная напрямую к проекту, НЕ
  переиспользует `StashSwatch` мотка (явное решение пользователя — образец
  проекта и образец мотка в хранилище не связаны, даже если структура полей
  совпадает): размер инструмента, плотность до/после ВТО, фото.
- **Описание, файл** — до 5 PDF-файлов на проект, до 20 МБ каждый (см.
  §8). **Независим** от блока «Описание» выше — можно приложить свой PDF
  даже если паттерн уже выбран из каталога (пользователь мог купить
  описание вне Раппорта). Личное пространство пользователя, без
  модерации содержимого (симметрично обычным фото в хранилище).
- **Референс** — фото для вдохновения/референса (не образец, не готовое
  изделие) — тот же UI-паттерн, что «Фото образца»/«Фото изделия»
  (перетаскивание порядка, первое фото — обложка блока). Отдельное поле
  на `Project`, не смешивается с `images`/`finishedPhotos`.
- **Фото изделия/этапа** — можно приложить уже при создании.
- **Заметки** — свободный текст; ограничение по высоте рамки (как в
  макете), при переполнении — скролл внутри рамки, а не жёсткий лимит
  символов.

### 0.3. Списание пряжи — модель зависит от способа появления статуса «Завершён»

Три разных пути, с разной механикой:

1. **Обычный жизненный цикл** (проект создан/живёт в статусе «В
   процессе»/«Пауза», статус меняется на «Завершён» С ЛЮБОГО ДРУГОГО
   статуса) → запускается отдельный **3-шаговый визард завершения**:
   - Шаг 1/3 — расход по каждому привязанному мотку → **реальное** списание,
     `StashSkein.currentWeightG` честно уменьшается через обычный
     `StashUsage` (как сейчас в `LogUsageWizard`).
   - Шаг 2/3 — уточнение названия/привязки к каталогу, если не было указано
     раньше.
   - Шаг 3/3 — фото готовой работы (несколько, с сортировкой, первое —
     обложка).
2. **Создание проекта СРАЗУ со статусом «Завершён»** (задним числом, для
   истории/портфолио — пользователь довязал вне приложения и заводит запись
   постфактум) → **визард не запускается**. Поле «Расход» и «Фото изделия»
   заполняются прямо в форме создания. Расход **не должен** искажать
   текущий физический остаток мотка (трата уже произошла ДО заведения мотка
   в приложение) — механика:
   - `StashSkein.totalWeightG += N`;
   - тут же создаётся `StashUsage(amountG: N, projectId: ...)`, которая по
     обычной логике спишет `N` с `currentWeightG`;
   - итог: `currentWeightG` не меняется относительно того, что было ДО
     заполнения формы, но `totalWeightG` и история списаний честно
     отражают, что расход был.
   - **Обязателен поясняющий попап** в момент, когда пользователь указывает
     расход для проекта, создаваемого сразу завершённым — коротко
     объясняющий эту механику (иначе непонятно, почему остаток мотка не
     меняется).
   - **Проверено при eng-review (см. §5): побочные эффекты роста
     `totalWeightG` на существующий UI — корректны, не требуют изменений.**
     `EditSkeinModal` уже не даёт снизить `totalWeightG` ниже суммы
     списаний (`weightValue < totalWeightG - currentWeightG`,
     `EditSkeinModal.tsx:190`) — после backdated-расхода это ограничение
     закономерно ужесточается: пользователь физически не может занизить
     объявленный вес мотка ниже уже подтверждённого (пусть и задним
     числом) расхода, что и требуется. Аналогично «Остаток: X из Y» на
     `SwipeableStashCard.tsx`/`StashSkeinDetails.tsx`/`LogUsageWizard.tsx`
     честно вырастет вместе с `totalWeightG` — это не баг отображения, а
     заявленный эффект операции (у мотка «было куплено больше, чем
     считалось»). Единственное реальное требование — пользователь должен
     узнать об этом эффекте ЗАРАНЕЕ, что и обеспечивает попап выше;
     дополнительный индикатор на самой карточке мотка сознательно не
     делаем (решено с пользователем — попап при вводе достаточен).
3. **Откат статуса «Завершён» → «В процессе»/«Пауза»** — списание **не**
   откатывается автоматически, история остаётся как есть. Повторный переход
   в «Завершён» → визард снова показывает шаг 1, но с **предзаполненными**
   значениями расхода из прошлого раза; если пользователь меняет цифру —
   существующая запись `StashUsage` **редактируется** через отдельный
   delta-guard механизм (см. §2.3 — **НЕ** тот же путь, что
   `EditUsageModal`/`updateUsage`: тот сознательно не даёт менять `amountG`
   вообще, см. комментарий в `stashController.ts:611-620`; редактирование
   веса списания в этой фиче требует новой атомарной операции, которой в
   текущем коде хранилища ещё нет), а не создаётся вторая запись.

Существующий флоу списания в хранилище (`LogUsageWizard`) **сохраняется как
есть**, сосуществует параллельно — оба пути пишут в одну и ту же таблицу
`StashUsage`.

### 0.4. Карточка проекта

Фото, кнопка редактирования, название, статус (dropdown прямо на карточке —
смена статуса отсюда тоже запускает визард завершения по правилам §0.3),
даты начала/завершения, описание, автор(ы). Разделы:

- «Пряжа» — список мотков (остаток, расход) + «Добавить пряжу»;
- «Образец» — список образцов проекта + «Добавить образец»;
- «Инструмент» + «Добавить инструмент»;
- «Заметки».

### 0.5. Удаление проекта

При удалении проекта, если есть связанные списания (`StashUsage`), нужно
явно спросить пользователя: вернуть списанный вес на остаток мотков, или
оставить историю списания как есть (не решать молча за пользователя).

### 0.6. Вероятные этапы развития (roadmap за пределами v1)

1. **Публикация проекта как примера работы** — флаг видимости
   (приватный/публичный) на проекте, показ на карточке описания («Смотрите,
   как связали это другие») и/или на карточке пряжи в общем справочнике
   («Что связали из этой пряжи»); потребует модерации, как у остального
   пользовательского контента.
2. **Отзывы и рейтинг пряжи/описания** — предложение оставить отзыв в шаге
   3 визарда завершения, пока опыт свежий; данные для рейтинга пряжи в
   справочнике и рейтинга описаний в каталоге.
3. **Социальный слой** — публичная лента/галерея чужих завершённых
   проектов, фильтруемая по описанию/артикулу пряжи; лайки, сохранение в
   избранное, профиль с портфолио.
4. **Обогащение аналитики подбора** — реальные данные о расходе пряжи на
   конкретное описание (вместо только теоретического расчёта по плотности,
   как в существующем `getMatches`/«Что можно связать»).
5. **Импорт из Ravelry Projects** — по аналогии с уже существующим Ravelry
   fallback для пряжи (`ravelryYarnFallback.ts`).

## 1. Модель данных (миграция, аддитивная)

### 1.1. `Project` — новая модель верхнего уровня

```prisma
model Project {
  id     String @id @default(uuid())
  userId String
  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)

  title  String
  status ProjectStatus @default(IN_PROGRESS)

  // Ручной ввод, когда паттерн не привязан (кнопка "Добавить вручную") —
  // НЕ то же самое, что author name у привязанного Pattern (тот берётся из
  // pattern.author.name на чтении, снимок не нужен — Pattern не удаляется
  // молча, как и у остальных живых связей в проекте).
  manualAuthor      String?
  manualDescription String?

  startedAt   DateTime  @default(now())
  completedAt DateTime?

  instruments Instrument[]

  note String?

  // Фото изделия/этапа, добавленные ПРЯМО В ФОРМЕ проекта, до завершения
  // (черновые фото процесса — "довязала рукав", "смотрю на цвет при
  // дневном свете"). Первое фото — обложка ДО завершения проекта, тот же
  // паттерн, что у StashSkein.images/StashSwatch.images.
  images String[] @default([])

  // Фото ГОТОВОГО изделия (шаг 3 визарда завершения, §3.1, ИЛИ форма
  // создания, если проект сразу заводится завершённым, §2.2) — единый
  // список НА ПРОЕКТЕ, один экземпляр ссылок на файлы независимо от
  // количества привязанных мотков пряжи (пересмотрено при обсуждении:
  // изначальный вариант плана копировал эти же ссылки в finishedPhotos
  // КАЖДОЙ связанной StashUsage — архитектурная ошибка, раздувающая
  // число мест, где хранится одно и то же, без всякой пользы; сами файлы
  // и так лежат
  // на диске в единственном экземпляре, копировались только ССЫЛКИ на
  // них, но и это было лишним обходным путём). Карточка мотка в хранилище
  // (блок "Связано") показывает эти фото ЧЕРЕЗ ССЫЛКУ на проект
  // (`usage.projectId` → `Project.finishedPhotos`), не хранит копию у
  // себя. Первое фото — обложка ПОСЛЕ завершения (приоритет над images
  // выше, см. правку ниже).
  finishedPhotos String[] @default([])

  // Фото для вдохновения/референса (блок "Референс" в обновлённом макете,
  // node-id=3039:31704) — НЕ то же самое, что images (готовое изделие/этап
  // СВОЕЙ работы) и НЕ образец (ProjectSwatch.images, плотность). Просто
  // визуальная подборка "что хочу связать похоже на это". Первое фото —
  // обложка блока, тот же паттерн перетаскивания порядка.
  referencePhotos String[] @default([])

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  patterns  ProjectPattern[]
  yarns     ProjectYarn[]
  swatches  ProjectSwatch[]
  usages    StashUsage[]
  documents ProjectDocument[]

  @@index([userId])
  @@index([status])
}

enum ProjectStatus {
  IN_PROGRESS
  COMPLETED
  PAUSED
}
```

**Решено с пользователем (пересмотрено после обсуждения — устраняет
находку, обнаруженную при этом пересмотре):** фото готового изделия
хранятся ОДИН РАЗ, прямо на `Project.finishedPhotos` — не копируются в
`StashUsage` привязанных мотков вообще. Обложка карточки проекта в
списке — `Project.finishedPhotos[0]`, если заполнено, иначе
`Project.images[0]` (черновые фото процесса, до завершения), иначе
плейсхолдер. Никакого JOIN на `StashUsage` для выбора обложки не нужно —
это устраняет саму проблему, из-за которой в предыдущей версии плана
здесь был долгий разбор "живого JOIN против кэша" (см. историю решений в
§5.2 — тот разбор был правильным ЛЕЧЕНИЕМ СИМПТОМА при неверной модели;
после переноса фото на `Project` симптом просто не возникает, потому что
источник данных больше не размножен по нескольким строкам).

Карточка мотка в хранилище (блок «Связано») показывает фото готового
изделия через переход по `StashUsage.projectId → Project.finishedPhotos`
— то есть **ссылкой на проект**, не собственной копией. Если сам `Project`
удалён, а `StashUsage` пережила это удаление (см. §0.5 — пользователь мог
выбрать "оставить историю списания") — фото просто негде взять, блок
«Связано» для такой записи показывает список без фото/плейсхолдер (то же
поведение, что уже есть сегодня для списаний без фото вообще).

### 1.2. `ProjectPattern` — join-таблица (many-to-many, с возможностью 0..N)

```prisma
model ProjectPattern {
  id        String   @id @default(uuid())
  projectId String
  project   Project  @relation(fields: [projectId], references: [id], onDelete: Cascade)

  // Nullable только из-за onDelete: SetNull (переживает удаление паттерна
  // из каталога) — при СОЗДАНИИ строки всегда заполнено: "ручной" паттерн
  // (кнопка "Добавить вручную" в форме) НЕ создаёт ProjectPattern вообще,
  // а пишет напрямую в Project.manualAuthor/manualDescription (§0.2). Живая
  // ссылка нужна для перехода на карточку описания из проекта, пока Pattern
  // существует — тот же принцип, что StashUsage.patternId.
  patternId String?
  pattern   Pattern? @relation(fields: [patternId], references: [id], onDelete: SetNull)

  // Снимок — пишется ВСЕГДА при создании строки, переживает удаление
  // паттерна из каталога (решено с пользователем, симметрично
  // StashUsage.patternTitleSnapshot/patternAuthorSnapshot).
  patternTitleSnapshot  String
  patternAuthorSnapshot String

  createdAt DateTime @default(now())

  @@unique([projectId, patternId])
  @@index([patternId])
}
```

### 1.3. `ProjectYarn` — join-таблица к `StashSkein`, переживает удаление мотка

```prisma
model ProjectYarn {
  id        String  @id @default(uuid())
  projectId String
  project   Project @relation(fields: [projectId], references: [id], onDelete: Cascade)

  // Nullable из-за onDelete: SetNull (см. ниже, эта правка — прямое
  // следствие eng-review находки #4: без SetNull удаление мотка из
  // хранилища КАСКАДНО унесло бы саму строку ProjectYarn, а вместе с ней
  // и видимость мотка в проекте — то есть уже реализованное сегодня
  // deleteSkein (onDelete: Cascade на StashSwatch/StashUsage.skein,
  // stashController.ts:379) молча стёрло бы и часть завершённого проекта.
  // Решено с пользователем: моток остаётся виден в проекте, теряется
  // только живая связь с хранилищем.
  skeinId String?
  skein   StashSkein? @relation(fields: [skeinId], references: [id], onDelete: SetNull)

  // Снимок — пишется ВСЕГДА при создании строки, переживает удаление
  // мотка из хранилища (симметрично ProjectPattern.patternTitleSnapshot/
  // patternAuthorSnapshot выше). Карточка проекта показывает ЭТИ поля,
  // если skeinId стал NULL, вместо живой карточки StashSkein.
  yarnNameSnapshot String
  brandSnapshot    String?

  // Снимок расхода (граммы) — пишется/обновляется СИНХРОННО с
  // StashUsage.amountG в той же транзакции (см. §2.3 — и при первом
  // списании, и при delta-guard редактировании после отката статуса).
  // NULL, пока StashUsage для этой пары ещё не существует (Project.status
  // != COMPLETED). Единственная причина дублирования, от которого
  // изначально сознательно отказались (см. пересмотр решения ниже):
  // StashUsage.skein сохраняет onDelete: Cascade (решено с пользователем
  // — история списания принадлежит мотку, ей можно исчезнуть вместе с
  // ним), поэтому при удалении StashSkein пропадёт и сама строка
  // StashUsage целиком, а вместе с ней — единственное место, где хранился
  // расход. amountAtCompletionG — это то, что остаётся в проекте, когда
  // источник правды уже физически удалён; НЕ читается, пока связанная
  // StashUsage жива (в этом случае JOIN на неё остаётся приоритетным
  // источником для UI, чтобы не было двух конкурирующих чисел при обычной
  // работе) — используется только как fallback, когда skeinId уже NULL.
  amountAtCompletionG Int?

  createdAt DateTime @default(now())

  @@unique([projectId, skeinId])
  @@index([skeinId])
}
```

**Пересмотрено после eng-review находки #4 (удаление мотка):** изначально
расход сознательно НЕ дублировался на `ProjectYarn` — единственным
источником было `StashUsage.amountG` через JOIN. Это было верно, пока не
обнаружилось, что `StashUsage.skein` сохраняет `onDelete: Cascade`
(решено с пользователем — история списания принадлежит мотку, может
исчезать вместе с ним, см. §1.5). Раз `StashUsage` может физически
исчезнуть, а расход в контексте ПРОЕКТА должен остаться видимым —
`amountAtCompletionG` возвращён как снимок-на-случай-удаления, не как
основной источник чтения. Правило одно: пока `skeinId` (и, следовательно,
связанная `StashUsage`) жив — UI читает через JOIN на `StashUsage.amountG`
(без риска рассинхрона в штатной работе); как только `skeinId` стал
`NULL` — единственный оставшийся источник это `amountAtCompletionG`.

**Важно:** `@@unique([projectId, skeinId])` с nullable `skeinId` в
Postgres допускает несколько `NULL` на один `projectId` (NULL не участвует
в проверке уникальности) — то есть после удаления сразу нескольких мотков
проекта уникальный индекс не помешает НИ ОДНОМУ из них корректно
занулиться, что и требуется (не единственность самого факта "мотка нет",
а единственность живой пары, пока она есть).

  isBackdatedCompletion Boolean @default(false)

  // ВАЖНО про уже существующее поле StashUsage.finishedPhotos (не
  // показано выше — оно не меняется структурно, но меняется правило
  // заполнения): пути этого плана (создание проекта сразу завершённым,
  // визард завершения) НЕ пишут туда ничего — фото готового изделия

  // сюда. Поле остаётся заполняемым ТОЛЬКО старым путём — обычным
  // списанием через LogUsageWizard в хранилище, никак не связанным с
  // проектами (там это по-прежнему единственное место хранения фото).
  // Для списаний с projectId != null это поле остаётся пустым всегда.

  @@index([projectId])
  // Не более одного списания на пару (проект, моток) — гарантирует, что
  // повторное прохождение шага 1 визарда после отката статуса (§0.3 п.3)
  // физически не может создать вторую запись, только найти и обновить
  // существующую. NULL в projectId не участвует в уникальности (обычные

  @@unique([projectId, skeinId])

**`skein StashSkein @relation(..., onDelete: Cascade)` (существующее поле,
без изменений) — рассмотрено и подтверждено при eng-review находки #4:**
удаление мотка из хранилища каскадно унесёт и связанные с проектом
`StashUsage` целиком — решено с пользователем оставить как есть (история
списания принадлежит мотку, вместе с ним может и исчезнуть), в отличие от
`ProjectYarn`/`ProjectPattern`, которые обязаны пережить это удаление на
уровне самого проекта (см. `ProjectYarn.amountAtCompletionG`, §1.3, куда
переносится снимок именно для этого случая). Это единственное сознательно
асимметричное решение в модели: проект помнит факт и число расхода, но не
обязан хранить сам объект `StashUsage`, если моток пользователь удалил.

### 1.6. `ProjectDocument` + `ProjectDocumentHighlight` — PDF-описания с выделениями (§8)

```prisma
model ProjectDocument {
  id        String  @id @default(uuid())
  projectId String
  project   Project @relation(fields: [projectId], references: [id], onDelete: Cascade)

  // Оригинальное имя файла — единственное, что видит пользователь в списке
  // (макет показывает "#sailor_polo.pdf" простой ссылкой), хранимое имя на
  // диске — отдельный сгенерированный uuid (см. §8.1, тот же приём, что у
  // stashUpload: filename не доверяем клиенту напрямую в качестве пути).
  originalFileName String
  storedFileName    String @unique
  fileSizeBytes     Int

  createdAt DateTime @default(now())

  highlights ProjectDocumentHighlight[]

  @@index([projectId])
}

// Выделение текста цветом внутри PDF (§8.2) — координаты через текстовый
// слой pdf.js, НЕ пиксельные координаты канваса (переживает смену
// масштаба/устройства с другим DPI, канвас — нет). Одна строка — один
// непрерывный диапазон выделения на одной странице; выделение через
// несколько строк текста на фронте разбивается на несколько записей (тот
// же приём, что использует стандартный PDF.js annotation editor).
model ProjectDocumentHighlight {
  id         String          @id @default(uuid())
  documentId String
  document   ProjectDocument @relation(fields: [documentId], references: [id], onDelete: Cascade)

  pageNumber Int
  // Прямоугольники в единицах PDF-страницы (не пикселях экрана) — один
  // textLayer-диапазон может визуально ломаться на несколько прямоугольников
  // (перенос строки), поэтому массив, не одно {x,y,w,h}.
  rects Json
  // HEX или именованный цвет маркера — фиксированная палитра на фронте
  // (см. §8.2), сервер не валидирует конкретные значения, только формат.
  color String

  createdAt DateTime @default(now())

  @@index([documentId])
}
```

**Почему аннотации — отдельная таблица, не модификация самого PDF-файла:**
сохранение выделения путём переписывания байтов PDF (через
`pdf-lib`/аналоги) сделало бы каждое новое выделение дорогой операцией
записи целого файла и создало бы риск повредить оригинал при частичной
записи. Хранение координат отдельно означает, что оригинальный
загруженный файл никогда не изменяется после `POST` — выделения нужно
просто оверлеить поверх канваса при каждом рендере (см. §8.2).

### 2.2. Создание проекта — `POST /projects`

Принимает все поля формы разом (§0.2): `title`, `status`, `startedAt`,
`completedAt?`, `manualAuthor?`/`manualDescription?` ИЛИ `patternIds:
string[]`, `instrumentIds: string[]`, `note?`, `images?: string[]`,
**`referencePhotos?: string[]`** (блок «Референс» из обновлённого макета,
§0.2/§1.1 — найдено при eng-review, находка B: поле уже было в схеме
`Project`, но отсутствовало в списке принимаемых API полей и там, и в
`PATCH`, исправлено здесь и в §2.1), `swatches?: [...]` (создаются
вложенно, тот же приём, что уже применяется в проекте для связанных
сущностей при создании родителя одним запросом).

**Список привязанной пряжи — ОДНО поле, форма зависит от `status`, не два
параллельных списка (устранена неоднозначность, найденная при
eng-review — находка #7):**
- `status !== "COMPLETED"` → `skeinIds: string[]` (просто список, без
  расхода — полю «Расход» неоткуда взяться, см. §0.3).
- `status === "COMPLETED"` → **вместо** `skeinIds` тело принимает
  `yarnUsages: { skeinId: string; amountG?: number }[]` — это ЕДИНСТВЕННЫЙ
  источник списка мотков в этом случае, `skeinIds` в теле игнорируется/не
  ожидается вовсе. Каждый элемент `yarnUsages` создаёт свой `ProjectYarn`
  независимо от того, указан ли `amountG` — привязка мотка к проекту и
  наличие расхода по нему разделены (**решено с пользователем: `amountG`
  необязателен для любого мотка** — можно привязать моток к
  сразу-завершённому проекту, не указывая расход; элементы без `amountG`
  порождают `ProjectYarn`, но не `StashUsage`). Так каждый `skeinId`
  встречается ровно в одном месте тела запроса — рассинхрон между двумя
  списками структурно невозможен, а не просто "предполагается, что
  совпадут".

Дополнительно при `status === "COMPLETED"` принимается `finishedPhotos?:
string[]` — пишется ОДИН РАЗ на `Project.finishedPhotos` (§1.1), не на
каждую `StashUsage` (пересмотрено — см. правку в §1.1, находка при
обсуждении: дублирование ссылок на фото по числу привязанных мотков было
архитектурной ошибкой). Обработка внутри одной транзакции:

1. Создать `Project` (включая `finishedPhotos`, если передано) и все
   связанные строки: `ProjectPattern`, `ProjectSwatch` — как обычно;
   `ProjectYarn` — по одной строке на каждый `skeinId` из `skeinIds`
   (если `status !== COMPLETED`) или на каждый `skeinId` из `yarnUsages`
   (если `status === COMPLETED`, см. правку выше §2.2) — включая
   `yarnNameSnapshot`/`brandSnapshot` из `StashSkein` на момент привязки
   (§1.3).
2. Для каждого элемента `yarnUsages` с непустым `amountG`:
   - `UPDATE "StashSkein" SET "totalWeightG" = "totalWeightG" + amountG
     WHERE id = skeinId` (тот же raw-SQL стиль, что в `logUsage`, но
     **плюс** к `totalWeightG`, а не guard на `currentWeightG` — здесь нет
     риска уйти в минус, наоборот, увеличиваем ёмкость);
   - следом обычная атомарная логика списания с `currentWeightG` (тот же
     `UPDATE ... WHERE currentWeightG >= amount`, что уже есть в
     `logUsage`) — в сумме `currentWeightG` не меняется относительно
     значения ДО этого запроса, что и требуется;
   - создать `StashUsage(amountG, skeinId, projectId: project.id,
     isBackdatedCompletion: true, projectTitle, patternTitleSnapshot,
     patternAuthorSnapshot)` — **БЕЗ** `finishedPhotos` (то поле остаётся
     заполняемым только старым путём, §1.5) — правило заполнения трёх
     "title/snapshot" полей общее для этой ветки и §2.3, см. врезку
     "Заполнение `StashUsage.projectTitle`/..." в начале §2.3;
   - `UPDATE "ProjectYarn" SET "amountAtCompletionG" = amountG WHERE
     "projectId" = project.id AND "skeinId" = skeinId` (снимок расхода на
     случай будущего удаления мотка, §1.3).
3. Если `status !== "COMPLETED"` — `yarnUsages`/`finishedPhotos` в теле
   игнорируются (расход и фото готового изделия недоступны вне статуса
   `COMPLETED`, см. §0.3); поле просто не должно присутствовать в форме на
   фронте в этом случае.

### 2.3. Смена статуса на «Завершён» — отдельная ветка, не через обычный PATCH

`PATCH /projects/:id` с `status: "COMPLETED"` в теле **отклоняется 400**,
если текущий `project.status !== "COMPLETED"` — обычный PATCH годится
только для правки полей БЕЗ смены на этот конкретный статус в эту сторону
(понижение из `COMPLETED` в `IN_PROGRESS`/`PAUSED` — обычный PATCH,
разрешено, списание не откатывается автоматически, см. §0.3 п.3).

Переход `IN_PROGRESS`/`PAUSED` → `COMPLETED` идёт **только** через
`POST /projects/:id/complete` (единый запрос на все 3 шага визарда сразу,
см. §3.1 — фронт копит состояние локально, шлёт один раз на «Сохранить»
после шага 3):

```
POST /projects/:id/complete
  body: {
    yarnUsages: { skeinId: string; amountG?: number }[]  // amountG может отсутствовать для любого мотка (§2.2 правка)
    patternIds?: string[]
    manualAuthor?: string
    manualDescription?: string
    title?: string
    finishedPhotos: string[]
  }
```

**Заполнение `StashUsage.projectTitle`/`patternTitleSnapshot`/
`patternAuthorSnapshot` — обязательно, найдено при eng-review (находка
#2).** Эти поля уже существуют и активно читаются существующим кодом
хранилища (`patternTitleSnapshot`/`projectTitle` заполняются сегодня в
`logUsage`/`updateUsage`, читаются как заголовок карточки в секции
"Связано" — `usage.projectTitle || 'Без названия'`,
`StashSkeinDetails.tsx:397`). Любая ветка этого плана, создающая или
обновляющая `StashUsage` (и здесь, и в §2.2), **обязана** заполнить:
- `projectTitle: project.title` — всегда, напрямую из названия проекта
  (не из паттерна — так подписи в хранилище единообразны независимо от
  того, привязан ли к проекту паттерн);
- `patternTitleSnapshot`/`patternAuthorSnapshot` — из **первого**
  `ProjectPattern` проекта, если есть (порядок — по `createdAt` первой
  привязки), иначе из `Project.manualDescription`/`manualAuthor`, иначе
  `null`. Если у проекта несколько паттернов — карточка в разделе
  "Связано" хранилища показывает только первый; это осознанное упрощение
  (та карточка одна строка на одно название, "несколько паттернов" туда
  physически не помещается без передизайна существующего компонента,
  который в v1 не трогаем) — полный список паттернов виден на самой
  карточке `ProjectDetails`, куда теперь и ведёт клик (§4.6).

Обработка в одной транзакции:

1. Для каждого элемента `yarnUsages` с непустым `amountG` — ищет
   существующую `StashUsage` по `(projectId, skeinId)`:
   - **Не найдена** — обычное атомарное списание + `CREATE`, тот же путь,
     что в `logUsage` (НЕ путь §2.2 механики "задним числом" —
     `currentWeightG` реально уменьшается, `totalWeightG` не трогается:
     проект жил в реальном времени, это не портфолио-случай), плюс
     `UPDATE "ProjectYarn" SET "amountAtCompletionG" = ${amountG}` для той
     же пары (снимок расхода, §1.3 — та же синхронизация, что и в ветке
     "Найдена" ниже).
   - **Найдена** (повторное завершение после отката, §0.3 п.3) — **НЕ**
     прямой `UPDATE amountG` и **НЕ** "логика `EditUsageModal`" (та
     сознательно не даёт менять `amountG` вообще, см.
     `updateUsage`/`stashController.ts:611-620` — комментарий там прямо
     объясняет почему: `amountG` завязан на `currentWeightG` через
     atomic-guard, отдельно от строки не редактируется). Нужен **новый
     delta-guard**, специфичный для этого случая — атомарно применяет
     РАЗНИЦУ между старым и новым значением, а не одно из двух чисел
     изолированно:
     ```sql
     UPDATE "StashSkein"
     SET "currentWeightG" = "currentWeightG" - (${newAmount} - ${oldAmount}),
         "updatedAt" = now()
     WHERE id = ${skeinId}
       AND "currentWeightG" - (${newAmount} - ${oldAmount}) >= 0
       AND "currentWeightG" - (${newAmount} - ${oldAmount}) <= "totalWeightG"
     ```
     — тот же принцип двойного guard'а, что уже есть раздельно в
     `logUsage` (нижняя граница) и `undoUsage` (верхняя граница), просто
     объединённый в одном выражении, потому что здесь меняется и то, и
     другое одновременно. При `affected === 0` — 400 "недостаточно пряжи"
     (увеличение расхода) либо теоретически недостижимо в обратную
     сторону (уменьшение расхода не может превысить `totalWeightG`, но
     guard оставлен симметрично для гонки двух параллельных запросов, тот
     же принцип, что `UndoWouldExceedTotalError`). Затем в той же
     транзакции — `UPDATE "StashUsage" SET "amountG" = ${newAmount} WHERE
     id = ...` **и** `UPDATE "ProjectYarn" SET "amountAtCompletionG" =
     ${newAmount} WHERE "projectId" = ... AND "skeinId" = ...` (снимок на
     случай будущего удаления мотка, §1.3 — обновляется синхронно в ОБОИХ
     местах, где создаётся/меняется `StashUsage` этого пути, чтобы никогда
     не разойтись с реальным `amountG`).
2. **`amountG: 0` и отсутствие поля `amountG` — РАЗНЫЕ команды (найдено
   при eng-review, требует явного различения):**
   - Элемент **отсутствует** в `yarnUsages` вообще, или `amountG` не
     передан для присутствующего элемента — **не трогать**: если для
     этой пары уже была `StashUsage` (повторное завершение после отката,
     §0.3 п.3) — она остаётся как есть; если не было — просто не
     создаётся.
   - `amountG: 0` **явно передан** — команда **обнулить**: если
     `StashUsage` для этой пары существовала — удаляется (тот же путь,
     что явное удаление мотка из проекта через `DELETE
     /projects/:id/yarns/:skeinId`, §2.4), вес возвращается на остаток
     мотка тем же delta-guard'ом (эквивалентно `newAmount = 0`); если не
     существовала — просто ничего не создаётся (нечего обнулять).
   - На фронте это означает: поле "Расход", очищенное пользователем до
     пустой строки, отправляется как ОТСУТСТВИЕ ключа `amountG` в объекте
     (не `amountG: 0`) — явный `0` возможен только если пользователь
     реально ввёл цифру 0, что интерпретируется как "в итоге эту пряжу не
     потратил".
3. Обновляет `patternIds`/`manualAuthor`/`manualDescription`/`title` на
   `Project`, если переданы.
4. Проставляет `finishedPhotos` на `Project.finishedPhotos` — ОДИН РАЗ, на
   самом проекте, не на связанные `StashUsage` (см. правку §1.1/§2.2:
   один список фото на весь проект, карточка мотка в хранилище подтягивает
   его по ссылке `usage.projectId → Project.finishedPhotos`, не хранит
   копию).
5. Только теперь — `Project.status = COMPLETED`, `Project.completedAt =
   now()` (если ещё не проставлено раньше).

фронтовая последовательность двух уже существующих вызовов.

### 2.5. Удаление проекта — `DELETE /projects/:id`

Тело: `{ returnYarnToStash: boolean }` (см. §0.5 — явный выбор
пользователя, не решается молча). Обработка в транзакции:

- Найти все `StashUsage` с `projectId = id`.
- Если `returnYarnToStash === true`: для каждой — вернуть вес на
  `currentWeightG` (`+= amountG`); если `isBackdatedCompletion === true` —
  **также** откатить `totalWeightG` (`-= amountG`), иначе искусственно
  увеличенная ёмкость мотка останется навсегда без причины (см. правку в
  §1.5 — комментарий про `isBackdatedCompletion` уже фиксирует эту
  асимметрию). Затем удалить сами строки `StashUsage`.
- Если `returnYarnToStash === false`: просто `UPDATE StashUsage SET
  projectId = NULL WHERE projectId = id` (история остаётся, ссылка на
  удалённый проект обнуляется — тот же принцип SetNull, что уже применяется
  к `patternId` при удалении `Pattern`).
- Удалить сам `Project` (каскадно унесёт `ProjectPattern`/`ProjectYarn`/
  `ProjectSwatch`/`ProjectDocument` через `onDelete: Cascade`) — удаляются
  только строки БД. Файлы, на которые ссылались `Project.images`/
  `finishedPhotos`/`referencePhotos`, `ProjectSwatch.images`,
  `ProjectDocument` (сам PDF), остаются на диске нетронутыми — общее
  правило проекта, см. §5.5.

## 3. Визард завершения — состояния и переходы

### 3.1. Диаграмма состояний (текстом)

```
[IN_PROGRESS/PAUSED] --(меняет статус на COMPLETED, любая точка входа:
                         dropdown на карточке ИЛИ форма редактирования)-->
   [визард открыт, step=1, Project.status ЕЩЁ НЕ изменён]
     -- "Закрыть" на любом шаге --> статус остаётся прежним (IN_PROGRESS/
        PAUSED), список расходов, введённых на step1, отбрасывается
        (ничего не сохранялось на backend до финального подтверждения)
     -- заполняет расход по мотку(-ам) (опционально — можно оставить
        пустым для любого мотка, см. §2.2 правку ниже), "Далее" -->
   [визард, step=2]
     -- уточняет название/каталог, "Далее" -->
   [визард, step=3]
     -- грузит фото, "Сохранить" -->
        ЕДИНЫЙ запрос на подтверждение всех 3 шагов разом, см. ниже —
        только теперь Project.status становится COMPLETED
   [визард закрыт] --> [COMPLETED, полностью заполнен]
```

**Решено с пользователем (меняет более раннюю версию этого раздела):**
проект не считается завершённым, пока визард не пройден целиком — если
пользователь закрывает визард кнопкой «Закрыть» на любом шаге, статус
**остаётся прежним** (откатывается назад, если что-то уже успело
измениться), а не зависает в `COMPLETED` без фото. Следствие для API:
вместо трёх независимых `POST .../complete/stepN`, каждый из которых
что-то сохраняет и меняет статус, нужен **один финальный эндпоинт**,
принимающий данные всех трёх шагов разом:

```
POST /projects/:id/complete
  body: {
    yarnUsages: { skeinId: string; amountG?: number }[]   // amountG опционален для любого мотка
    patternIds?: string[]
    manualAuthor?: string
    manualDescription?: string
    title?: string
    finishedPhotos: string[]
  }
```

Промежуточные шаги на фронте — чисто клиентское состояние визарда
(локальный React state, не отдельные сетевые запросы), отправка на backend
происходит один раз, на шаге 3 («Сохранить»). Это проще и надёжнее, чем
три отдельных запроса с откатом промежуточных при закрытии — нет
необходимости в компенсирующих транзакциях для отмены уже сохранённого
шага 1/2, если пользователь передумал на шаге 3.

### 3.2. Создание сразу завершённым (§0.2/§2.2) — визард НЕ используется

Единый `POST /projects` со `status: "COMPLETED"` в теле выполняет то, что
в обычном жизненном цикле собирается через визард одним `POST
/projects/:id/complete` (см. §2.3), но за один запрос вместе с созданием
самого `Project`. Разница с `.../complete`: механика §0.3 п.2
(искусственное увеличение `totalWeightG`, `isBackdatedCompletion: true`),
а не обычное списание — это ЕДИНСТВЕННОЕ техническое различие между
«завершил через визард» и «создал сразу завершённым», всё остальное
(структура `StashUsage`, `finishedPhotos`, снимки паттерна, необязательность
`amountG`) идентично.

### 4.3. Условная логика полей формы проекта (`AddProjectModal`/`EditProjectModal`)

Единая длинная форма (§0.2), но с состоянием, зависящим от других полей —
не статичный список input'ов:

1. **Блок «Описание»**:
   - Состояние `descriptionMode: 'search' | 'manual' | 'none'`.
   - `search` — поле поиска + список результатов (как `AddYarnModal`'s
     Ravelry-подсказки, тот же паттерн debounce + список карточек), при
     выборе — фиксирует `patternId`, переключает соседнее поле «Название»
     в режим «название проекта» (автор берётся из паттерна на бэкенде,
     фронт просто не показывает поле «Автор»).
   - `manual` — активируется кнопкой «Добавить вручную» при пустой выдаче
     поиска; показывает два поля: свободный «Автор» + свободное
     «Описание/название проекта».
   - `none` — пользователь просто не трогал блок «Описание» вообще;
     `Project.title` (обязательное поле) остаётся единственным
     идентификатором проекта.
2. **Блок «Статус»** — при выборе `COMPLETED` **показывает** дополнительные
   поля на уровне каждой карточки уже выбранной пряжи в блоке «Пряжа»
   («Расход», см. п.3) и появляется секция «Фото готовой работы» (не то же
   самое, что «Фото изделия/этапа» выше по форме — оба поля видны
   одновременно при статусе `COMPLETED`, разные назначения, см. §1.1 про
   приоритет обложки). При выборе `IN_PROGRESS`/`PAUSED` — оба этих
   элемента скрыты.
3. **Блок «Пряжа»** — при `status !== COMPLETED` карточка мотка в списке
   показывает только «убрать»/остаток, без поля «Расход» (см. §0.3). При
   `status === COMPLETED` — под каждой привязанной карточкой появляется
   input «Расход» (опционален, см. §2.2), и при первом вводе значения
   (`onBlur`/`onChange` от 0 к непустому) показывается
   `BackdatedCompletionNotice` **только если форма — это создание нового
   проекта** (не редактирование существующего в процессе — там расход при
   статусе `COMPLETED` уже прошёл через обычный визард, искажения
   остатка нет, объяснять нечего).
4. **Блок «Инструмент»** — при выборе паттерна в блоке «Описание»,
   чекбоксы предзаполняются из `pattern.instruments` (см. §0 «Предзаполняем
   инструменты по выбранному описанию, но всегда даём изменить») — то есть
   выбор паттерна ПОСЛЕ того, как пользователь уже вручную поправил
   чекбоксы, не должен молча перезаписывать его выбор (предзаполнение
   срабатывает только при первом выборе паттерна, не при каждом
   изменении).

### 4.4. Текст поясняющего попапа (§0.3 п.2, закрывает открытый вопрос §5.2)

Показывается один раз при первом заполнении поля «Расход» для мотка в
форме создания проекта сразу со статусом «Завершён» (не при каждом мотке,
если их несколько — попап один на всю форму, флаг «уже показан» в

> **Черновой текст (для дизайн-ревью, не финал):**
> «Вы создаёте уже завершённый проект — например, чтобы сохранить его в

### 5.3. Третий проход — вопрос пользователя вскрыл архитектурную ошибку в §5.2 п.1

При обсуждении критерия "какую из нескольких StashUsage читать для
обложки" (техническая деталь решения из §5.2 п.1) пользователь задал
более фундаментальный вопрос: зачем вообще хранить одну и ту же
фотографию (точнее, одну и ту же ссылку на файл) в нескольких строках
`StashUsage`, если к проекту привязано несколько мотков? Живой JOIN из
§5.2 п.1 решал симптом (устаревание при удалении мотка), но не устранял
причину — сам факт, что `finishedPhotos` дублировался по числу мотков,
хотя семантически это один и тот же список "фото готового изделия
проекта", не мотка.

**Итоговое решение:** `finishedPhotos` перенесено на `Project` (§1.1) —
единственное место хранения, независимо от числа привязанных мотков.
`StashUsage.finishedPhotos` (существующее поле) остаётся заполняемым
только старым путём (`LogUsageWizard` в хранилище, не связанным с
проектами) — новые пути этого плана его больше не трогают вообще (§1.5,
§2.2, §2.3). JOIN для выбора обложки стал не нужен — карточка проекта
читает `Project.finishedPhotos[0]` напрямую, карточка мотка в хранилище
(блок «Связано») подтягивает те же фото по ссылке `usage.projectId →
Project`, а не хранит копию.

**Уточнение про сами файлы (не про ссылки в БД), явно проговорённое
пользователем:** удаление `Project` не должно вызывать немедленное
физическое удаление файлов на диске, если на них может ссылаться что-то
ещё в приложении. **Проверено по коду — это уже и так гарантировано, без
какой-либо новой работы:** во всём проекте сегодня нет ни одного места,
которое удаляло бы файл с диска при удалении записи, ссылающейся на него
(`deleteSkein`/`deleteSwatch`/`deletePattern` и т.п. удаляют только строки
БД, `fs.unlink` для удаления не встречается нигде в контроллерах —
проверено по `stashController.ts`). Значит требование "не удалять файл,
пока есть хоть одна ссылка" выполняется автоматически как побочный эффект
того, что физическое удаление файлов не реализовано вообще нигде в
проекте — это её текущее (осознанно принятое ранее, не в рамках этого
плана) поведение, не то, что нужно спроектировать заново для `Project`.

### 5.5. Общее правило работы с изображениями/файлами — применено по всему плану и проверено против ВСЕГО существующего кода

**Правило (сформулировано пользователем как обязательное "везде", не
только для находки §5.3):**
1. Между сущностями копируются ТОЛЬКО ссылки (пути/URL) на уже
   загруженный файл, никогда не сам файл повторно.
2. Каждый файл хранится и показывается из ОДНОГО места, к которому
   относится по смыслу; остальные места, которым он тоже нужен для
   отображения, переходят по ссылке на это место, а не хранят свою копию
   пути.
3. Физическое удаление файла с диска НЕ происходит при удалении
   ссылающейся на него записи БД — если возможно, что ссылка есть
   в другом месте, файл остаётся; если такой возможности в принципе нет
   (файл 1-к-1 с одной записью, как `ProjectDocument`, §8.1) — всё равно
   не удаляется, потому что это единое правило по всему проекту, а не
   специфичное для конкретного типа медиа исключение, которое пришлось бы
   каждый раз обосновывать заново.

**Найдено и исправлено при системной проверке этого плана против кода
(по прямому запросу пользователя "проверь весь план"):**

- **`ProjectYarn`/`amountAtCompletionG`/`yarnNameSnapshot`/
  `brandSnapshot`** (§1.3) — это СНИМКИ ЧИСЕЛ И ТЕКСТА (переживают
  удаление источника, потому что источник может физически исчезнуть), НЕ
  копии файлов — правилу не противоречат: снимок значения поля ≠ копия
  файла.
- **`ProjectSwatch.images`** (§1.4) — самостоятельный список фото
  конкретного образца ПРОЕКТА, не пересекается ни с `StashSwatch.images`
  (образец мотка — явно решено как отдельная несвязанная сущность, §0.2),
  ни с `Project.images`/`finishedPhotos`/`referencePhotos` — не
  дублирование, три разных набора фото с разным назначением.
- **`Project.finishedPhotos`** (§1.1/§5.3) — главная находка этого
  правила: изначальный черновик плана копировал одни и те же ссылки на
  фото в `finishedPhotos` КАЖДОЙ связанной `StashUsage` (по числу

## 7. Полный набор пользовательских сценариев

Термины ниже соответствуют финальной модели данных из §1–§3 (`Project`,
`ProjectPattern`, `ProjectYarn`, `ProjectSwatch`, `StashUsage.projectId`).

### Группа A — способ найти/привязать описание

**A1. Из каталога Раппорта, по названию/автору.** `AddProjectModal` →
поиск в блоке «Описание» → выбор результата создаёт `ProjectPattern`
(снимок title/author пишется сразу) → «Название»/«Инструмент» подставляются
автоматически, редактируемы.

**A2. Ничего не найдено — ввод вручную.** Поиск пуст → «Добавить вручную»
→ `descriptionMode = 'manual'` → `Project.manualAuthor`/
`manualDescription` вместо `ProjectPattern`.

**A3. Без привязки к описанию вообще.** Только `Project.title` +
обязательные статус/дата начала, блок «Описание» не тронут
(`descriptionMode = 'none'`).

**A4. Несколько описаний на один проект.** Повторный выбор в блоке поиска
создаёт вторую строку `ProjectPattern` на тот же `projectId`.

### Группа B — работа с пряжей

**B1. Пряжа уже в `StashSkein`.** Поиск по хранилищу → выбор → `POST
/projects/:id/yarns` (или вложенно при создании, см. §2.2) создаёт
`ProjectYarn`.

**B2. Пряжи нет в запасах, есть в справочнике.** Пусто в `StashSkein` →
переход к `GET /stash/yarns/suggest` → выбор → `POST /stash/skeins`
(создание нового мотка) → `POST /projects/:id/yarns` тем же вызовом
последовательности, что и обычное «Добавить пряжу» в хранилище (см. §2.4.1
— переиспользование, не новая backend-логика).

**B4. Несколько мотков на проект.** Повтор B1/B2 — несколько строк
`ProjectYarn` на один `projectId`.

### Группа C — статусы и жизненный цикл

**C1. Обычный жизненный цикл.** Создание `IN_PROGRESS` без расхода (поля
«Расход» нет, см. §0.3) → редактирование/дозаполнение образцов и заметок
→ опционально `PAUSED` и обратно → смена на `COMPLETED` (dropdown на
карточке ИЛИ форма редактирования) → визард (§3.1, локальное состояние,
единый `POST /projects/:id/complete` на шаге 3) → `StashSkein.currentWeightG`
реально уменьшается, `StashUsage.isBackdatedCompletion = false`.

**C2. Отмена завершения.** `COMPLETED` → откат на `IN_PROGRESS` через
обычный `PATCH` (списание НЕ откатывается, §0.3 п.3) → снова `COMPLETED` →
визард запускается заново, шаг 1 предзаполнен текущими `StashUsage.amountG`
по паре `(projectId, skeinId)` → изменение значения при повторном
`/complete` обновляет существующую строку (гарантия — уникальный индекс
`StashUsage(projectId, skeinId)`, §1.5), не создаёт вторую.

**C3. Проект «для истории» (портфолио).** `POST /projects` сразу со
`status: COMPLETED` → механика §0.3 п.2/§2.2 (`totalWeightG += N`,
`StashUsage(amountG: N, isBackdatedCompletion: true)`, `currentWeightG` не
меняется) → `BackdatedCompletionNotice` показан один раз при первом вводе
расхода (§4.3 п.3, §4.4) → визард НЕ запускается.

**C4. Удаление проекта.** `DELETE /projects/:id` с явным выбором
`returnYarnToStash` (§2.5) — при `true` откатывает `currentWeightG` (и
`totalWeightG`, если `isBackdatedCompletion`), при `false` — только
`StashUsage.projectId = NULL`, история остаётся.

### Группа D — просмотр и редактирование

**D1. Просмотр карточки.** `GET /projects/:id`, все секции из §0.4.

**D2. Дозаполнение постепенно.** Кнопки «Добавить пряжу»/«Добавить
образец»/«Добавить инструмент» на `ProjectDetails.tsx` — точечные `POST
/projects/:id/{yarns,swatches,instruments}` без пересохранения всей формы.

**D3. Переход в связанные карточки.** Из `ProjectDetails` — на `Pattern`/
`StashSkein`; из `StashSkeinDetails`, секция «Связано» — на `Project`, если
`usage.projectId` заполнено (§4.6), иначе на `Pattern` как раньше.

## 8. PDF-описания с выделением текста (добавлено после начала проектирования)

Дополнение к макету, полученное в процессе работы над этим планом
(node-id=3039:31704/32158) — блок «Описание, файл» в форме проекта и
блок «Референс». Модель данных — §1.6. Технически самая нетривиальная
часть v1: единственное место в проекте, требующее рендер PDF внутри
WebView и хранение выделений отдельно от файла.

### 8.1. Хранение и раздача файла — НЕ через публичный `/uploads`

**Критично, отличается от всех остальных медиа в проекте:** PDF содержит
платный контент, купленный пользователем вне Раппорта (§0, диалог) — в
отличие от фото хранилища/образцов/проектов, раздающихся как обычный
публичный статик (`app.use("/uploads", express.static(...))` в
`index.ts:126`, без какой-либо авторизации), файл описания не должен быть
доступен по угадываемому/расшаренному URL кому угодно.

- Директория загрузки — **вне** `apps/backend/uploads/` (той, что примонтирована
  на `express.static`), например `apps/backend/private/project-documents/`.
- `POST /projects/:id/documents` — `multer.diskStorage` в эту приватную
  директорию, `storedFileName` — `uuid + ".pdf"` (не оригинальное имя —
  тот же принцип, что уже применяет `stashUpload` в `routes/stash.ts`, но
  без последующего вызова `normalizeUploadedImage`/`sharp`: PDF не
  изображение, обработка контента не нужна, только сохранение как есть).
- Валидация: MIME `application/pdf` **и** проверка сигнатуры файла (первые
  байты `%PDF-`) — расширение/MIME из `multipart` легко подделать, а это
  единственный тип загрузки в проекте, где содержимое не проходит через
  `sharp` (та библиотека неявно валидирует, что байты — реально
  декодируемое изображение; PDF-эквивалента такой проверки в текущем
  пайплайне нет, значит нужно добавить явно).
- `GET /projects/documents/:id/file` — **новый паттерн для проекта**:
  авторизованный эндпоинт (`loadOwnedProject`-подобная проверка через
  `documentId → projectId → userId`), стримит файл через
  `res.sendFile`/`fs.createReadStream`, не полагаясь на `express.static`.
  Обязательный `Content-Disposition: inline` (не `attachment`) — чтобы
  Telegram WebView открывал PDF-viewer компонента (см. §8.2), не
  скачивание.
- Лимиты: до 5 файлов на проект, до 20 МБ каждый (решено с пользователем)
  — те же два guard'а, что `MAX_STASH_IMAGES_PER_SWATCH`/`_SKEIN`, только
  на количество строк `ProjectDocument` и `multer` `limits.fileSize`.
- **Физическое удаление файла — то же общее правило проекта, что и для
  фото (см. §5.5): не удаляем.** `DELETE /projects/documents/:id` и
  каскадное удаление через `DELETE /projects/:id` убирают только строку
  `ProjectDocument` из БД, файл на диске остаётся. В отличие от фото
  (которые МОГУТ быть на что-то ещё сослаться, см. §5.5), PDF-файл всегда
  1-к-1 с одной строкой `ProjectDocument` — но правило то же самое не
  потому, что кто-то другой может ссылаться, а потому что это единое
  правило работы с загруженными файлами по всему проекту, а не
  специфичное для конкретного типа медиа обоснование, которое пришлось бы
  каждый раз доказывать заново.

### 8.2. Viewer и выделение текста — pdf.js на фронте

Новая зависимость `pdfjs-dist` в `apps/frontend-miniapp` (сейчас
отсутствует в проекте, см. проверку `package.json` на момент этого
плана) — единственная широко используемая библиотека, дающая доступ к
текстовому слою PDF в браузере/WebView без серверного рендеринга в
картинки.

**Компонент `PdfViewerModal.tsx`** (новый, полноэкранный шит поверх
карточки проекта, открывается по клику на ссылку `#filename.pdf`):

1. Грузит бинарь через `GET /projects/documents/:id/file` (с
   авторизационным заголовком — тот же `authorizedFetch`, что везде во
   фронте, не голый `<a href>`, раз эндпоинт требует авторизации).
2. Рендерит текущую страницу на `<canvas>` (`page.render(...)` из
   pdf.js) + невидимый (но кликабельный/выделяемый) `<div>` текстового
   слоя поверх канваса, спозиционированный тем же способом, что
   стандартный `pdfjs-dist/web/pdf_viewer` `TextLayerBuilder`.
3. **Выделение цветом** — слушает `selectionchange` в текстовом слое;
   при непустом выделении показывает всплывающую панель с палитрой
   цветов маркера (фиксированный набор — 3-4 цвета, как в макете
   остальных цветовых акцентов проекта); выбор цвета вызывает
   `getClientRects()` на `Range` выделения, конвертирует пиксельные
   прямоугольники обратно в координаты PDF-страницы (обратное
   преобразование той же матрицы viewport, что использовалась при
   рендере — стандартный приём pdf.js, `viewport.convertToPdfPoint`) и
   шлёт `POST /projects/documents/:id/highlights`.
4. При каждом открытии страницы — подгружает существующие
   `ProjectDocumentHighlight` для неё и рисует полупрозрачные
   `<div>`-прямоугольники поверх текстового слоя в сохранённых
   координатах (та же прямая матрица viewport, применённая в обратную
   сторону).
5. Удаление выделения — тап по уже закрашенному прямоугольнику →
   подтверждение → `DELETE /projects/documents/highlights/:id`.

**Не входит в v1 (см. §6):** экспорт PDF с "выжженными" в файл
выделениями (флэттенинг аннотаций в сами байты документа) — используется
только оверлей поверх канваса при просмотре внутри приложения; свободное
рисование/фигуры/текстовые заметки поверх страницы (только highlight по
текстовому слою, решено с пользователем).

### 8.3. Референсные фото — без новой инфраструктуры

Блок «Референс» (`Project.referencePhotos`, §1.1) технически не требует
ничего нового — тот же upload-пайплайн, что `images`/`ProjectSwatch.images`
(`normalizeUploadedImage` + `sharp`, публичный `/uploads/`, обычные фото
без прав доступа) — просто ещё один массив полей на форме, не отдельный
раздел плана. Упомянут здесь только для полноты описания макета (§0.2).

**Проверка перед переходом к Этапу 3 — выполнена вручную через curl
против локального сервера/БД** (сценарий C2 из §7 и удаление в обоих
режимах `returnYarnToStash`). Найдены и исправлены 2 реальных бага,
не видных при простом чтении кода:

1. **`createProject` (backdated-механика, §2.2)** — исходная реализация
   делала `totalWeightG += amountG`, затем ОТДЕЛЬНЫМ запросом
   `currentWeightG -= amountG` с guard'ом `currentWeightG >= amountG`.
   На мотке с маленьким остатком (`currentWeightG=20`) и большим расходом
   (`amountG=320`) guard справедливо отклонял операцию (`20 < 320`), хотя
   по замыслу плана результат должен был быть "currentWeightG не
   меняется вообще". **Исправлено:** убрано изменение `currentWeightG` из
   этой ветки полностью — единственное реальное действие backdated-
   механики это `totalWeightG += amountG`, `currentWeightG` не
   трогается ни в одну, ни в другую сторону (они бы всё равно
   взаимоуничтожились).
2. **`deleteProject` (откат backdated-списания, §2.5)** — тот же класс
   ошибки симметрично: при `returnYarnToStash: true` для
   `isBackdatedCompletion` списаний код делал `currentWeightG +=
   amountG` ОДНОВРЕМЕННО с `totalWeightG -= amountG` — то есть трогал
   поле, которое при создании не менялось. **Исправлено:** для backdated
   списаний откатывается ТОЛЬКО `totalWeightG`.

Оба бага проверены end-to-end на реальной локальной БД (создание с
`currentWeightG=20/totalWeightG=750/amountG=320` → корректно
`currentWeightG=20/totalWeightG=1070`; повторное завершение с delta
`320→340` → ровно одна строка `StashUsage`, `currentWeightG` уменьшился
на разницу 20; `amountG: 0` → строка удалена, вес возвращён; удаление
backdated-проекта с `returnYarnToStash: true` → откатился только
`totalWeightG`; с `false` → история осталась, `projectId` обнулился, веса
не тронуты).
