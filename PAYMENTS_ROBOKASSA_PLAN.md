# Приём оплат через Robokassa — варианты решения (черновик для обсуждения)

Документ только для обсуждения. Кода не пишет, ничего в проекте не меняет.
Цель — разложить задачу на решения, которые нужно принять, и предложить
рекомендованный вариант по каждому, опираясь на то, что уже есть в проекте
(`PAID_TIER_PERMISSIONS_PLAN.md`, `PAID_TIER_ROLLOUT_PLAN.md`).

## 0. Что уже есть в проекте и на что это влияет

Прежде чем проектировать оплату, важно то, что инфраструктура доступа **уже
построена** под именно такой сценарий:

- В схеме есть `Permission` (`PREMIUM_CORE`, `PREMIUM_EXTRA`,
  `PREMIUM_DETAILS`) + join-таблица `UserPermission` — сейчас выдаются
  вручную через админку.
- Middleware `resolveRole` уже резолвит разрешения пользователя на каждый
  запрос с TTL-кэшем 30 сек — то есть выдача/снятие доступа подхватывается
  бэкендом почти сразу, без переавторизации.
- `PAID_TIER_PERMISSIONS_PLAN.md` §7 прямо оставляет маркер: *"когда
  появится оплата — обработчик успешного платежа должен вызвать ровно ту же
  логику выдачи, что и админ-чекбоксы"*. То есть точка интеграции
  спроектирована заранее.
- Есть отдельный сервис `telegram-gateway` — общий шлюз для отправки
  сообщений от бота (уже используется несколькими проектами, включая этот).
  Это готовый канал для напоминаний о продлении, слать которые нужно не
  через сам мини-апп (пользователь может его не открывать), а через бота.
- Есть прецедент "экрана-гейта" — `SubscriptionRequired.tsx`, полноэкранная
  блокировка по признаку `isSubscriber`. **Это не про платную подписку** —
  это проверка подписки на Telegram-канал. Термины пересекаются по
  созвучию, но это два независимых механизма. Ниже я использую словосочетание
  "платная подписка" только для оплаты, чтобы не путать с `isSubscriber`.

Вывод: основную часть "выдать доступ" писать не нужно — нужно **достроить
слой оплаты сверху** существующей permission-модели, а не проектировать
права доступа заново.

## 1. Пользовательский путь целиком

```
1. Пользователь открывает мини-апп.
2. Раз в N дней (предлагаю раз в неделю, как вы и написали) — если у
   пользователя нет активной платной подписки — показывается баннер/шторка
   с рассказом о преимуществах платного тарифа и кнопкой "Оформить".
3. Клик по кнопке → пользователь видит короткую страницу оплаты внутри
   мини-аппа (цена, срок действия, что входит) → кнопка "Оплатить".
4. Клик "Оплатить" → бэкенд создаёт запись о платеже (статус "ожидает") →
   отдаёт фронту готовую ссылку на страницу оплаты Robokassa с подписью.
5. Мини-апп открывает эту ссылку — ВАЖНО: не внутри Telegram WebView, а во
   внешнем браузере (см. §3.4) — пользователь платит на стороне Robokassa
   (карта / СБП).
6. Robokassa после успешной оплаты:
   а) синхронно шлёт запрос на сервер (Result URL / webhook) — это
      единственный источник правды о том, что деньги реально пришли;
   б) параллельно редиректит пользователя обратно в браузере на "успешную"
      страницу — она нужна только для UX ("оплата прошла, вернитесь в
      приложение"), доступ по ней НЕ выдаём (см. §3.3, почему это критично).
7. Бэкенд на Result URL: проверяет подпись → находит платёж по номеру
   заказа → пишет дату оплаты → выдаёт нужные permission-флаги (вызывает ту
   же логику, что и админ-чекбоксы) → отвечает Robokassa "ОК".
8. Пользователь возвращается в мини-апп (вручную или по кнопке "Вернуться в
   приложение" на странице Robokassa) — видит, что платные функции уже
   доступны (permission уже в БД, следующий же запрос к API его подхватит).
9. За несколько дней до окончания месяца — бот присылает пользователю
   напоминание о продлении со ссылкой на страницу оплаты.
10. Если оплата не продлена к моменту истечения — плановая задача (cron)
    снимает платные permission-флаги тем же способом, что и админ вручную.
```

Ниже — по каждому шагу отдельно, с вариантами и открытыми вопросами.

## 2. Баннер "раз в неделю"

**Где считать "было показано".** Два варианта:

| Вариант | Плюсы | Минусы |
|---|---|---|
| `localStorage` на клиенте | Ничего не трогать на бэкенде, быстро сделать | Слетает при переустановке/очистке, не работает если пользователь заходит с двух устройств, нет аналитики на бэкенде |
| Поле на `User` (например, дата последнего показа) | Переживает переустановку, видно в БД/аналитике, легко посчитать конверсию | Нужна одна миграция + один эндпоинт "отметить показ" |

**Рекомендация:** поле на `User`, а не `localStorage` — в проекте уже есть
похожий паттерн трекинга (`SubscribeClick`, `PatternLinkClick` — append-only
таблицы событий), можно either добавить одно nullable-поле на `User`, либо
завести ещё одну append-only таблицу по аналогии (`PaywallImpression`), если
вам важна история показов, а не только "последний раз". Разница в цене
реализации минимальна, поле на `User` — самый дешёвый вариант, append-only
таблица — самый гибкий (если позже понадобится A/B тест текста баннера,
частоты показа и т.п.).

**Когда НЕ показывать** (независимо от частоты):
- у пользователя уже есть активная платная подписка;
- пользователь только что закрыл баннер в эту сессию (не долбить повторно
  при каждом переходе между экранами);
- (опционально) пользователь явно нажал "не показывать больше" — стоит
  решить, нужна ли такая кнопка, или еженедельный показ и так достаточно
  ненавязчив.

**Форма.** Предлагаю не блокирующий полноэкранный гейт (как
`SubscriptionRequired`), а закрываемую шторку/баннер (bottom sheet или
карточка сверху каталога) — блокировать доступ к бесплатному контенту ради
рекламы платного тарифа обычно бьёт по удержанию сильнее, чем ненавязчивое
предложение. Если хотите жёстче — можно сделать раз в неделю полноэкранным,
но с явной кнопкой "продолжить бесплатно" — вопрос вкуса продукта, не
инфраструктуры.

## 3. Оплата через Robokassa

### 3.1. Способ интеграции: простая forma vs API

У Robokassa два основных способа принять платёж:

1. **Redirect-схема (Simple Invoicing)** — бэкенд формирует URL с суммой,
   номером заказа и подписью (MD5-хэш от логина/суммы/номера/пароля),
   отдаёт его фронту, пользователь переходит на страницу Robokassa напрямую.
   Никакого API-клиента, ключей помимо двух паролей из личного кабинета не
   нужно.
2. **API-интеграция** (создание счёта через HTTP-запрос к Robokassa,
   получение ссылки в ответе) — даёт чуть больше контроля (например,
   получить ссылку без реального редиректа пользователя, показать своё UI
   до перехода), но добавляет ещё один сетевой вызов и обработку ошибок API.

**Рекомендация:** вариант 1 (redirect-схема с подписанным URL) — для
именно такого сценария (один тариф, фиксированная цена, оплата раз в месяц)
она полностью покрывает потребность и на порядок проще в реализации и
отладке. К API-интеграции есть смысл переходить, только если понадобится
динамическое ценообразование или несколько тарифов с разными сценариями.

### 3.2. Разовый платёж vs автосписание (рекуррентные платежи)

То, как вы описали флоу ("через месяц напоминаем и либо продлевает, либо
отключаем") — это **разовый платёж с ручным продлением**, не автосписание.
Это важно явно зафиксировать, потому что Robokassa поддерживает и второй
вариант (рекуррентные платежи, автоматическое списание без участия
пользователя каждый период), и его тоже стоит рассмотреть, но с
оговорками:

| | Разовый + напоминание (как вы описали) | Рекуррент (автосписание) |
|---|---|---|
| Реализация | Проще — нет токена для повторного списания, нет отдельного статуса подписки | Сложнее — Robokassa должна быть отдельно подключена под рекуррентные платежи, первый платёж должен явно получить согласие на автосписание и токен для повторных списаний |
| Юридически | Проще — не нужен отдельный явный consent-текст на автосписание | Требует чёткой формулировки в оферте/при оплате ("N ₽ будет списываться ежемесячно, отменить можно здесь") — иначе жалобы/чарджбэки |
| Отток | Выше — часть пользователей просто забудет продлить | Ниже — стабильнее MRR |
| UX отключения | Естественно "истекает само" | Нужна явная кнопка "отменить автосписание" |

**Рекомендация:** начать с разового платежа + напоминания — именно то, что
вы и предложили. Это меньший объём работы, не требует отдельного
юридического согласия на автосписание, и полностью тестируемо на реальных
пользователях без риска "списали деньги без явного нового действия
пользователя", что обычно вызывает больше всего жалоб на старте. Переход к
рекурренту — естественное развитие уже после того, как разовая схема
обкатана, если отток окажется существенным.

### 3.3. Result URL vs Success URL — критичный момент безопасности

У Robokassa три URL, которые нужно настроить в личном кабинете:

- **Result URL** — сервер-сервер запрос от Robokassa на ваш бэкенд, **после**
  того как деньги реально зачислены. Это единственное место, откуда должен
  выдаваться доступ.
- **Success URL** — редирект браузера пользователя после оплаты, чисто для
  UI ("спасибо, оплата прошла"). Пользователь может оказаться на этой
  странице, просто вручную подставив URL с любыми параметрами — **выдавать
  доступ по факту захода на Success URL нельзя**, это открытая дыра
  ("бесплатный доступ", просто зная формат ссылки).
- **Fail URL** — редирект при неудачной/отменённой оплате, тоже только UI.

Это единственный пункт, где стоит быть особенно внимательным при реализации
— частая ошибка в интеграциях именно такого типа платёжек — гейтить доступ
на клиентском редиректе вместо серверного вебхука.

**Проверка подписи.** Проверено по актуальной документации
(`docs.robokassa.ru/ru/notifications-and-redirects`), формулы точные:

- Исходящая ссылка на оплату: `MerchantLogin:OutSum:InvId:Пароль#1`.
- Result URL (вебхук): `OutSum:InvId:Пароль#2` (без пользовательских
  `Shp_*`) или `OutSum:InvId:Пароль#2:Shp_key=value` (с ними, отсортированы
  по алфавиту).
- Success URL, если решите там тоже сверять подпись (не обязательно —
  доступ по ней всё равно не выдаём): `OutSum:InvId:Пароль#1` — **не**
  Пароль#2.

Пароль#2 отдельный от Пароля#1, оба выдаются в личном кабинете. Проверка
подписи на Result URL обязательна: без неё любой, узнавший URL эндпоинта,
может подделать запрос "оплата прошла" и получить доступ бесплатно.

**Формат ответа на Result URL.** Не просто "OK" — буквально `OK{InvId}`
без пробела, например `OK5`.

**Готча парсинга суммы.** В тестовом режиме `OutSum` в Result-запросе
приходит с 2 знаками после запятой, в боевом — с **шестью**. Если
обработчик сравнивает сумму как строку с фиксированной точностью — тест
пройдёт, а первый боевой платёж сломается.

**Белый список IP**, если на бэкенде есть фильтрация входящих запросов:
`185.59.216.65`, `185.59.217.65` — иначе Result URL может быть
недостижим для Robokassa.

**Идемпотентность.** Robokassa повторяет запрос на Result URL, если не
получила ожидаемый ответ (`OK{InvId}`) — обработчик должен быть
идемпотентным: если платёж с этим номером заказа уже отмечен оплаченным —
просто повторно ответить `OK{InvId}`, не выдавать permission дважды (не
страшно самим по себе, `UserPermission` и так уникален по `(userId,
permission)`, но важно для корректности даты/срока подписки — не сдвигать
`paidAt`/дату окончания повторно от ретрая).

### 3.3a. Чек для самозанятого — параметр `Receipt` и интеграция с «Мой налог»

Уточнение к тому, что раньше говорилось про "чек формируется автоматически,
без ручных действий" — это верно только частично.

**Активация для самозанятого — не просто "подключить Мой налог".**
Согласно `robokassa.com/online-check/robocheck-smz/`: *"Для подключения
самозанятого достаточно дать разрешение на интеграцию в приложении «Мой
налог» и сервис Робочеки СМЗ автоматически активируется."* — то есть
конкретное действие внутри самого приложения «Мой налог» (раздел
партнёров/интеграций → разрешить Robokassa), не просто факт регистрации
как самозанятого в приложении. Стоит явно проверить, что сделан именно
этот шаг.

**Решено: передаём `Receipt` всегда, по умолчанию.** Документация не даёт
стопроцентной ясности, обязателен ли этот параметр именно для самозанятых
через "Робочеки СМЗ" (раздел про `Receipt` явно написан для 54-ФЗ,
ИП/ООО) — но это не повод ждать ответа поддержки перед стартом. Решение
простое: не гадаем, а просто всегда формируем и передаём `Receipt` с
одной позицией (название — по описанию тарифа, `quantity: 1`, `sum` =
`OutSum`, `tax: "none"` — самозанятые не плательщики НДС). Если параметр
окажется необязательным для "Робочеки СМЗ" — лишним он не будет; если
окажется обязательным — он уже на месте. Не блокер для начала кода;
единственное, что стоит сделать — специально проверить в тестовом прогоне
(§7, шаг 5), что чек/квитанция реально формируется и выглядит корректно,
до первого боевого платежа.

### 3.4. Success/Fail URL и Telegram-гейт мини-аппа

Отдельная проблема, не про Robokassa, а про сам мини-апп: пользователь
после оплаты попадёт на Success/Fail URL **в обычном браузере**, не в
Telegram (он туда попал через `openLink`, см. §3.5). `App.tsx` детектит
отсутствие Telegram-окружения и покажет экран "Откройте в Telegram" вместо
"Оплата прошла" — тот же класс проблемы, что и с публичной страницей
оферты (§9.4). Решение то же: `success.html`/`fail.html` статикой в
`apps/frontend-miniapp/public/`, в обход гейта в `App.tsx`, с кнопкой-
диплинком обратно в бота.

### 3.5. Открытие ссылки оплаты из Telegram Mini App

Отдельный нюанс именно для мини-аппа: банковские страницы оплаты (3-D
Secure, СБП) часто не открываются корректно внутри встроенного webview
Telegram — их следует открывать через `Telegram.WebApp.openLink(url)`
(открывает системный браузер), а не через `openTelegramLink` (тот
предназначен для t.me-ссылок, уже используется в проекте в
`SubscriptionRequired.tsx`, но не годится для внешнего домена Robokassa) и
не через встроенный `<a>`/iframe. Это чисто техническая деталь реализации,
но её стоит держать в голове на этапе оценки — без неё часть пользователей
будет видеть, что оплата "зависает" или не проходит 3-D Secure.

### 3.6. Тестовый режим

У Robokassa есть тестовый режим (`IsTest=1` в запросе + тестовые
учётные данные в личном кабинете) — позволяет прогнать весь флоу (создание
ссылки → оплата тестовой картой → Result URL → выдача доступа) без реальных
денег. Стоит заложить в план как отдельный обязательный шаг перед первым
реальным платежом.

## 4. Самозанятость: чеки и налоги

Это отдельный блок, не чисто технический, но напрямую влияет на архитектуру
(нужно ли хранить/показывать ссылку на чек, кто его формирует).

- Для самозанятого (НПД) закон обязывает выдавать чек по каждому поступлению
  от физлица — обычно сразу или не позднее 9-го числа следующего месяца, но
  на практике безопаснее формировать сразу при оплате, не откладывать.
- У Robokassa есть партнёрская интеграция с "Мой налог" — при регистрации
  точки приёма как самозанятый и подключении профиля "Мой налог" в личном
  кабинете, чек по успешному платежу формируется автоматически на стороне
  Robokassa, без ручных действий. Это стоит проверить/уточнить в актуальном
  личном кабинете при регистрации — детали интеграции у платёжных
  провайдеров периодически меняются, и я не хочу утверждать точный текущий
  UX, не видя ваш конкретный кабинет.
- Ставка налога — 4%, т.к. плательщики физлица (пользователи мини-аппа), а
  не юрлица/ИП.
- Годовой лимит дохода для статуса самозанятого — 2,4 млн ₽. Не блокер для
  старта, но стоит держать в уме как операционный потолок, если тариф
  выстрелит — при приближении к лимиту потребуется либо ограничивать приём
  оплат, либо переходить в статус ИП.
- Если автоматическая интеграция с "Мой налог" по каким-то причинам
  недоступна — резервный вариант — вручную регистрировать чек через
  приложение "Мой налог" по каждому платежу. Это не масштабируется (ручная
  операция на каждый платёж) и подходит только для проверки на малом
  количестве первых платежей, не как постоянный процесс.

**Открытый вопрос вам:** зарегистрирована ли уже точка приёма в личном
кабинете Robokassa как самозанятый, и подключён ли "Мой налог"? Если нет —
это первый шаг вне кода, без него нет смысла тестировать даже в тестовом

## 5. Данные: что нужно добавить в схему

**Решено (см. разбор в §6):** дата истечения доступа НЕ живёт в
`UserPermission` и не требует правки `resolveRole` — она денормализована
на `User`. Состав схемы:

**5.1. История платежей** — новая таблица (условно `Payment`), чистая
история/бухгалтерия, в логике доступа не участвует: номер заказа
(уникальный числовой ID — Robokassa требует именно числовой `InvId`, не
UUID, значит нужен отдельный счётчик/sequence, не переиспользовать `id` в
UUID-формате остальных моделей), сумма, статус (ожидает / оплачен /
просрочен), `userId`, дата создания, дата фактической оплаты (то самое
"фиксируем дату оплаты" из задачи). Ссылку/ID чека от "Мой налог" здесь
хранить не обязательно, раз чек шлётся в бот, а не показывается в
интерфейсе (§8, п.5) — но факт "чек отправлен" стоит отметить, чтобы
обработчик не отправлял его повторно при ретраях Result URL.

**5.2. Срок действия доступа** — одно денормализованное поле,
`User.premiumExpiresAt` (nullable `DateTime`), в духе уже существующего в
этой же схеме паттерна (`Pattern.imageUrl`, который бэкенд поддерживает
синхронно с `images[0]` при каждой записи — см. комментарий в
`schema.prisma`). Платёжный webhook перезаписывает его при каждой успешной
оплате; `UserPermission` — без изменений схемы вообще, сама выдача/снятие
флагов работает ровно так же, как сегодня для админки — cron лишь вызывает
ту же функцию revoke по расписанию, а не человек руками.

## 6. Напоминание и отключение — job на юзера vs дата+проверка на чтении

Вы предложили сравнить два варианта: (A) отдельная плановая задача на
каждого пользователя, или (B) дата действия разрешения + проверка "не
протухло ли" на чтении, с отключением платных функций при протухании.
Ниже — почему ни то, ни другое в чистом виде не оптимально именно для
этого проекта, и что предлагаю вместо них.

**(A) Job на каждого пользователя** (очередь с отложенными задачами вроде
BullMQ/Agenda, где при оплате заводится персональный таймер "сработать
через 30 дней") — требует завести саму эту инфраструктуру, которой в
проекте сегодня нет: `PAID_TIER_ROLLOUT_PLAN.md` прямо фиксирует, что кэш
роли — простой `Map` в памяти процесса, "в проекте сейчас нет
кэш-инфраструктуры вообще". Заводить очередь с Redis ради одной фичи —
явный оверинжиниринг.

**(B) Чистая ленивость** (дата на `UserPermission`, `resolveRole`
фильтрует "на лету", никакого cron нет вообще) — сама по себе была бы
самой простой, но есть нюанс, специфичный именно для этого проекта:
`UserPermission` читается не только через `resolveRole`. Как минимум ещё в
двух местах — сборка ответа `POST /auth/telegram` (`permissions[]` для
фронта) и админка (`getPermissions` / чекбоксы в карточке пользователя).
Если проверку "не протухло" добавить только в `resolveRole` — эти два
места будут молча показывать "доступ есть", когда его по факту уже нет.
Это не гипотетический риск: `PAID_TIER_PERMISSIONS_PLAN.md` §3.4 описывает
ровно такой же баг, уже дважды случившийся в этом проекте (`useIsAdmin`
проверял не то поле в разных местах фронта). Ленивость технически проще,
но переносит риск рассинхронизации на "не забыть продублировать проверку
везде", а именно это здесь уже подводило.

**Рекомендация — третий вариант:** один общий daily cron (по образцу уже
существующего `check_price_updates.py`, который тоже гоняется по
расписанию, дважды в день) — не персонально на юзера, один скрипт на всех
пользователей разом. Он **физически снимает** флаги через уже готовую
`revokePermission`. После снятия все существующие места чтения
(`resolveRole`, ответ логина, админка) продолжают работать буквально без
единой правки — для них "доступ снят" выглядит так же, как если бы админ
вручную снял чекбокс, потому что это технически то же самое действие.
Дата (`User.premiumExpiresAt`) нужна только этому одному cron-скрипту —
больше нигде в кодовой базе о ней знать не нужно.

Один и тот же ежедневный прогон делает два независимых шага:
- у кого `premiumExpiresAt` наступает через 3 дня и напоминание ещё не
  отправлено — напоминание в бот через `telegram-gateway`;
- у кого `premiumExpiresAt` уже в прошлом, а флаги ещё не сняты —
  `revokePermission(PREMIUM_CORE)` + `revokePermission(PREMIUM_EXTRA)`.

**Grace period получается бесплатно.** Раз cron суточный, а не мгновенный
— доступ снимается не в секунду истечения, а в течение следующих ≤24
часов. Это и есть тот 1 день, который вы сочли приемлемым — не нужно
кодировать его отдельной логикой, он просто следует из частоты запуска.
Если захочется короче — это правка расписания (например, каждые 6 часов),
не изменение логики самого скрипта.

**Открытый вопрос от этого разбора:** повторная оплата до истечения
(продление "с запасом") — новый `premiumExpiresAt` считать от `now()`
(пользователь теряет оставшиеся дни текущего периода) или от текущего
значения `premiumExpiresAt`, если оно ещё в будущем (дни суммируются)?
Зафиксировал в §8.
