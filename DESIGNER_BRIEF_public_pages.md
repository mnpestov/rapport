# Бриф дизайнеру: 4 публичные страницы (вне Telegram)

Контекст для дизайнера: это не экраны мини-аппа. Это 4 обычные веб-страницы,
которые открываются в **обычном мобильном браузере** (Safari/Chrome), не
внутри Telegram — пользователь либо специально переходит по ссылке
(оферта/политика), либо его туда редиректит банк/Robokassa после оплаты
(success/fail). Внутри Telegram эти страницы не показываются вообще.

Фактически это не 4 разных дизайна, а **2 шаблона с вариантом состояния**:

- **Шаблон А — «юридическая страница»**: `oferta.html` + `privacy.html`.
- **Шаблон Б — «результат оплаты»**: `success.html` + `fail.html` (один макет,
  два состояния — успех/неуспех).

Стилистика — не обязана совпадать с `DESIGN_SYSTEM.md` в репозитории (та
палитра описана как «Rapport **Admin**» — для служебной админки, не для
пользовательской части). Для этих 4 страниц ориентир — визуальный стиль
самого мини-аппа (то, что видит пользователь в каталоге/карточке описания),
не админка.

## Шаблон А — юридическая страница (`oferta.html`, `privacy.html`)

**Задача:** длинный юридический текст должен быть читаем на телефоне и
содержать реквизиты продавца — это не просто вежливость, это отдельное
требование модерации Robokassa (реквизиты должны быть видны на самой
странице, не только внутри текста договора).

**Структура сверху вниз:**

1. Небольшая шапка — необязательно сложная: название/лого продукта,
   по желанию — ссылка «Открыть в Telegram» (для случайно зашедшего сюда
   человека). Не функциональный элемент, просто чтобы страница не выглядела
   сиротливо оторванной от продукта.
2. Заголовок документа (H1):
   - `oferta.html` → «Публичная оферта о заключении договора об оказании услуг»
   - `privacy.html` → «Политика обработки персональных данных»
3. Основной текст — пронумерованные разделы (1, 2, 3…), у оферты внутри
   разделов ещё и подпункты. Нужна чёткая иерархия заголовков (H2 для
   разделов), комфортный интерлиньяж для длинного текста, без двух колонок
   — один столбец, читается сверху вниз.
4. **Блок реквизитов** — вынести визуально отдельно (карточка/подложка,
   не просто последний абзац сплошного текста), обязательно содержит:
   - Самозанятый Пестова Юлия Юрьевна
   - ИНН 410116038191
   - г. Москва
   - Telegram-бот: `@rapportapp_bot`
   - E-mail: `pestovauu@yandex.ru`
5. Перекрёстная ссылка на второй документ (из оферты — на политику, и
   наоборот).

**Источник текста:** финальный текст обоих документов уже готов —
`oferta_410116038191.docx` и `privacy_policy_410116038191.docx` в корне
репозитория. Дизайнеру нужна только вёрстка/структура, не сочинение текста
(один абзац в оферте про состав тарифа сейчас помечен как черновик —
финальную формулировку утвердим до вёрстки, но структурно место под него уже
понятно — идёт внутри раздела «Цена и порядок расчётов»).

**Не нужно:** ни поиска, ни меню, ни интерактивных элементов кроме двух
ссылок (друг на друга + опционально на бота). Это read-only документ.

## Шаблон Б — результат оплаты (`success.html` / `fail.html`)

**Задача:** пользователь только что закрыл банковское приложение/страницу
оплаты и попал сюда — это эмоционально значимый момент («получилось» или
«не получилось»), в отличие от шаблона А стоит уделить дизайну больше
внимания. Одна и та же структура макета, два состояния.

**Структура (единая для обоих состояний):**

1. Иконка/иллюстрация статуса — на усмотрение дизайнера (галочка для success,
   нейтральная — не тревожная — иконка для fail; это не системная ошибка,
   а обычная незавершённая оплата, тон должен быть спокойный, не алармистский).
2. Заголовок:
   - `success.html`: «Оплата прошла успешно»
   - `fail.html`: «Оплата не прошла»
3. Поясняющий текст:
   - `success.html`: подтверждение + что дальше. Черновик копирайта:
     *«Подписка активна. Платные функции появятся в приложении в течение
     минуты. Чек придёт вам в Telegram-бот.»*
   - `fail.html`: снятие тревоги + что дальше. Черновик копирайта:
     *«Средства не списаны. Вы можете попробовать оформить подписку ещё
     раз.»*
4. Основная кнопка (CTA), крупная, по центру:
   - `success.html`: «Вернуться в приложение»
   - `fail.html`: «Попробовать снова»
   - Обе ведут обратно в Telegram-бота/мини-апп — **точный формат
     диплинка ещё нужно уточнить на моей стороне** (открыть именно
     мини-апп, а не просто чат с ботом) — для вёрстки это просто кнопка-
     ссылка, адрес подставим позже.
5. Мелкий текст под кнопкой — контакт поддержки на случай проблемы:
   - `success.html`: *«Если доступ не появился в течение нескольких минут —
     напишите нам»* + ссылка на `@rapportapp_bot`.
   - `fail.html`: *«Если деньги всё же списались — напишите нам»* + та же
     ссылка.

**Не показывать:** сумму, номер заказа или другие параметры из адресной
строки — страница не должна выглядеть так, будто она отображает
«официальные» данные платежа (их источник — сама Robokassa/бот, не эта
статическая страница).

## Технические ограничения (важно для дизайна, не только для вёрстки)

- Мобильный экран — основной сценарий, десктоп — вторичный (но не должен
  выглядеть сломанным).
- Страницы полностью статические — без авторизации, без чтения состояния
  пользователя, без анимаций, требующих JS-логики. Рендерятся одинаково
  для любого посетителя в любой момент.
- Один общий визуальный «каркас» (шапка + при необходимости футер) на всех
  четырёх — чтобы они читались как единая система, а не 4 не связанных
  друг с другом экрана.
